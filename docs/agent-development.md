# Agent 使用、开发与下一步能力建设

本项目面向需要查询、排障和巡检业务系统的团队。要获得可靠的 Agent，先让一个真实问题具备明确目标、授权能力和可核对的证据，再扩大自动化范围。本章对应工作空间的「AgentScope 入门」，说明从现有能力出发如何开发、验证与扩展；尚未实现的能力单独列为后续方向。

2026-10-08 核查入门页路线后完成一轮基础迭代。截图中的三项方向仍有缺口，优先列表还漏了查询前目标绑定：既有合成实验复现了模型在授权范围内换错目标仍实际查询。随后增加了本轮用户显式确认的单工具、单对象只读目标绑定：策略声明 `requiredTargetFields` 后，Node 在实际调用前精确核对资源、工具、环境及全部参数字段。自由文本和附件不会被解析为可信目标，未配置该策略的工具仍按原有授权工作；本机真实 DTS 资源已显式同步至修订 3，真实链路验收单独记录。质量方面原已有合成 DTS 评测、候选源码摘要和待人审验收，本轮新增脱敏样本/标注校验台账；用户随后授权从本机历史筛选，台账现含一条历史合成场景观察失败及一条原工作空间 DTS 复查 user-role 消息的脱敏候选。后者有会话文件和用户提供截图相互印证，但应用角色不能独立证明真人作者，且它处于接入验收会话，因此标记为 `historical_candidate`，不计入真实用户问题；两条人审仍 pending，`real_problem` 与 `human_review` 均阻断。观测方面原已有单轮问答全景和阶段耗时指标，续轮增加默认关闭的 OTLP/HTTP JSON 出口及可选模型/MCP `traceparent` 传播；尚无生产 Collector 验收、跨实例聚合或供应商账单。执行方面原已有独立 Worker 与应用容器限额，本轮把 Python 临时文件归入每轮私有目录，并新增独立沙箱协议与本机合成探针；产品仍没有不可信代码执行入口、租户文件/网络隔离或产物审批。具体实测见 [验证记录](verification.md)。

实现依据见 [前端组件地图](../src/components/codemap.md)、[Agent 运行时地图](../server/agent-runtime/codemap.md) 和 [Worker 地图](../agent-worker/codemap.md)。SDK 为 AgentScope 2.0.8，使用 Python 3.12；所有新聊天与定时 Agent 任务统一使用该运行时。固定工具、审批和 Runbook 使用 Node 治理执行器，不伪装成 AgentScope 模型编排。

续轮为两条合成重构问题的质量回放增加逐条结果复核模板与检查，绑定原报告及候选摘要，详见[运行指南](agentscope-runtime.md#脱敏质量样本台账)和[OpenSpec](../openspec/changes/agentscope-quality-replay-review-20261008/proposal.md)。用户授权后，Codex 先拒绝漏报四个必需字段的受控答复，修正夹具使其引用本轮实际工具结果，再完成两条 AI 工程复核。记录区分 AI、人工和未声明类型；AI 完成不计为人工验收。待验收项不影响启动、继续开发或使用现有功能。历史来源核实、真实模型质量和发布评测仍需完成；保存模型在一次真实查询后曾超时，仍需重复稳定性验收。

## 用项目学习 Agent 与准备面试

进入「AgentScope 入门 → 学习与面试」，按六个主题查看原理、真实源码位置、已有实验命令及预期观察。先尝试口述，再展开参考回答；每课可填写自评和实验笔记，切课会保留，切换上方视图、离开页面或刷新会丢失，可提前导出 `agent-learning-notes.md`。页面不会执行命令、调用模型或业务工具；自评不是测试通过或能力认证。

完整[学习路线](agent-learning.md)分为八个单元，进一步展开 Worker 边界与流式处理；[面试与项目复盘](agent-interview.md)提供十组追问、两个工程案例及按真实贡献改写的简历模板。后续以[迭代台账](learning-evolution.md)推进一个个小实验，先取得证据，再扩大能力。

## 第一次使用：跑通可核对的一轮

进入导航中的「AgentScope 入门」。页面的模型状态来自当前工作空间配置，资源计数来自当前用户可见的资源列表，不扫描其他用户的私有资源，不连接模型或 MCP 做探测。

| 顺序 | 要做的事 | 完成后检查什么 |
| --- | --- | --- |
| 准备模型 | 管理员在头像菜单的工作空间设置配置并测试模型 | “已保存配置”不等于当前供应商可用；需要实际问答验证 |
| 1. 定义 Skill | 选择只读巡检、知识问答或日志分析模板，编辑输入条件、步骤和输出要求 | 模板符合实际业务，未包含凭据、硬编码实时值或虚构工具名 |
| 2. 按需接 MCP | 查询实时数据时由管理员维护 Streamable HTTP 服务、允许列表和工具策略 | 核对只读 / 写入风险、Schema、目标范围、上游账号权限与核验方法 |
| 3. 按需建子领域 | 指令或能力存在明确干扰时，绑定该子领域需要的 Skill、知识与 MCP | 子领域和 Skill 均已发布且启用；资源绑定不自动扩大资源读者权限 |
| 4. 发起问答 | 复制、修改示例问题，新建对话并选择 Agent 后发送 | 目标与环境明确，样例服务名已换成自己的授权目标 |
| 5. 回看问答全景 | 展开本次回答的「问答全景」，查看节点、依赖和异常 | 工具证据是否实际取得，来源与目标是否一致，是否还有缺口 |

没有指令冲突时可直接使用通用 Agent，不必为了使用 AgentScope 再创建子领域。静态资料问答也不要求 MCP；但“系统现在正常吗”不能仅凭静态手册作答。只读权限也不等于无风险，范围限制仍应由后端策略和上游服务执行。

### 模板如何成为可用 Skill

引导页提供可编辑的 `SKILL.md` 与示例问题。不同场景的编辑在当前页面挂载期间各自保留；离开页面或刷新后丢弃。复制、编辑、下载都不会创建资源、调用模型或执行工具。浏览器不允许剪贴板写入时页面提示选中文本手动复制；模板还可通过下载按钮保存。

复制提示只属于最近一次仍有效的操作。切换场景或上方视图、编辑模板/示例问题、新复制、下载和离页后，旧复制请求的迟到成功/拒绝不再更新提示，也不会覆盖新下载提示。这不撤销浏览器已接受的写入，粘贴后仍应核对内容。

1. 下载后保留文件名 `SKILL.md`，按真实业务修改。模板中的 `demo-service`、`test` 和日志占位内容仅用于教学。
2. 将 `SKILL.md` 压缩为 ZIP。入口可以在 ZIP 根目录或唯一一层文件夹中。
3. 前往「Skill技能」上传，检查元数据、正文和文件列表，再保存草稿。
4. 按既有审核规则发布并启用。编辑已经发布的 Skill 会回到草稿，需要重新发布。
5. 在明确授权的目标上验证典型问题、缺失信息、无权限目标、工具失败与证据不足。

Skill 包附件被保存但不会自动加入上下文，上传的 Shell、Python 等脚本不执行。页面内的自然语言限制只能引导模型，不能代替资源权限、工具策略、参数 Schema 或远端账号授权。ZIP 限额、发布流程和教学工具见 [运维接入实操](ops-onboarding.md) 与 [上下文和工具](context-and-tools.md)。

引导计数按以下规则计算：Skill / 子领域必须 `status=已启用` 且 `publication=published`；MCP 必须启用且允许列表非空。它没有证明允许列表内工具全部存在、策略有效、网络可达或绑定正确，也没有把任意资源的存在当作当前模板已经可运行。

### 怎样判断第一次问答有效

至少检查以下三类情况：

- **正常路径**：目标不变，工具只调用允许范围，回答能够指向实际取得的资料 / 观测。
- **缺口路径**：缺少目标、资料、连接或新鲜数据时，明确说明待确认内容，不能因未发现异常就宣称健康。
- **边界路径**：目标不在授权范围、证据带有恶意指令、模型试图执行写入或更换目标时，权限门禁和结果核验仍生效。

「独立复核」默认关闭，开启后由分析 Agent 产生候选答案，再由无工具的独立 Agent 复核；只有通过才发布候选。它增加一次模型调用，可能误判，也不能撤销之前已发生的查询。真实质量收益仍需评测；详见 [运行指南](agentscope-runtime.md)。

问答全景呈现系统记录的处理过程和依赖，不展示模型的私有思考链。实际执行记录、业务健康判定与人工审批是不同事实；工具发现或模型回答完成不能代替业务系统健康，回答生成时的快照也不代表后续审批后的最新状态。

## 开发：把修改放在正确边界

### Node 负责权限与执行，Python 负责编排

| 位置 | 当前职责 | 扩展时的约束 |
| --- | --- | --- |
| `src/components/AgentScopeGuide.tsx` | 当前资源状态说明、场景模板、复制与本地下载、开发边界 | 不在浏览器推断后端授权，不把教学模板计为实际执行 |
| `server/agent.mjs` | 准备授权资源与上下文，固定本轮策略，组织模型与工具，保存消息 | 权限检查与治理状态保持在 Node，不能只靠提示词 |
| `server/agent-runtime/` | SDK 私有协议、模型桥接、原始工具参数校验、进程管理、取消和预算 | 维护协议终态与不重放规则，Worker 不选用户、数据库路径或供应商地址 |
| `agent-worker/worker.py` | AgentScope `Agent` + `ReActConfig`，通过 `ModelBridge` 与外部工具事件请求 Node 执行 | 不直接使用供应商密钥，不替换 Node 权威消息，不直接连接业务 MCP |
| `server/execution.mjs` | 持久执行、排队、幂等、工具步骤、审批、核验与取消 | 有副作用的动作仍走同一个门禁，不另建绕过策略的执行通道 |
| `server/model.mjs` | 模型协议与出口、流式正文、用量 | 流式展示不能绕过终态和复核门禁，推理与工具参数不向用户界面转发 |

prefork 父进程仅预加载锁定 SDK，每轮在独立子进程创建 Agent 和事件循环；cold 每次重新启动解释器。两者是同一 SDK 的启动方式，不是不同的 Agent 引擎。Node 与 Worker 经私有 stdin/stdout 交换版本化消息，没有内部 HTTP 执行入口。

新业务能力通常沿着下面路径扩展：

- **工作方法**：增加 Skill 和验收问题；需要稳定资料则维护知识库。
- **外部数据 / 操作**：增加受限 MCP 工具，给出真实 Schema、风险类别、范围、幂等和只读核验设计。
- **指令与能力冲突**：在实际证据支持时用子领域分流，避免仅按组织架构堆叠 Agent。
- **编排变化**：修改 Node ↔ Worker 协议和运行时，并覆盖调用预算、取消、崩溃、终态、权限变更及 cold / prefork。

开始 DTS 集成前还必须阅读 [DTS 交接说明](../integrations/dts-mcp/HANDOFF.md)。本次引导没有新增 DTS 工具或修改上游业务系统。

### 本地验证顺序

在仓库根目录准备 Node ≥ 22.16、Python 3.12 和 uv，然后执行：

```sh
uv sync --project agent-worker --frozen
npm run agent:check
npm run agent:eval
```

`agent:check` 是真实 SDK 的本地内存模型 / 外部工具往返，不打开业务数据库或访问真实供应商。默认 `agent:eval` 使用本地受控模型与 MCP fixture，对比 cold / prefork；它能验证桥接和工具选择链路，但不证明真实诊断质量、供应商容量或生产系统健康。

修改行为后按仓库规则运行匹配的专项和完整门禁：

```sh
npm test
npm run build
npm run docs:build
npm run docs:check
```

修改运行时另做 cold 模式与故障场景回归；修改界面另做浏览器、键盘与 320px 布局检查。以上是可复现步骤，实际本轮结果与未验证项统一记入 [验证记录](verification.md)，不把命令清单当作已经通过的证据。

## 沙箱：已具备的隔离与需要补齐的能力

### 从界面了解本机部署和验收

打开「AgentScope 入门 → 部署与验收」，或直接访问 `http://localhost:5173/#guide?tab=deployment`。「开始使用」页也有显眼的「了解部署与验收」入口，不必先读命令或 JSON 报告。

观测区解释 Collector 接收问答路径、Tempo 保存链路、Prometheus 汇总次数/耗时的分工，展示管理员本次检查时间和连通结果，提供统计页面入口与查询示例。Collector 的响应只表示接收入口可达；沙箱状态只检查 MCP 入口，不代表 broker 容量或本次代码已执行。历史服务验收记录有自己的测量时间与检查项，不能当作当前源码或生产验收。

账单区支持管理员直接选择两份 CSV/JSON，点击「开始对账」查看金额和 tokens 差额、未匹配项、抵扣与分币种汇总，并下载结果。可以先「载入演示数据」：估算0.10 USD、账单0.12 USD，实际对账显示0.020000 USD差额，明确标为演示。页面每份文件最多400 KiB，超出时使用本机CLI；JSON金额必须使用十进制字符串。数据经当前服务器内存计算，不落盘或发送模型，切换文件清除旧结论，来源未验证不自动当作真实账单验收。

沙箱区展示固定代码→独立写审批→隔离运行与回收→产物预览/批准下载的实际流程，说明支持的语言、产物与限额，并根据当前可见 MCP 允许列表标明是否接入。入口可达与历史隔离/清理验收分开显示；从这里可进入「MCP服务」核对接入，不会因浏览页面而执行代码。普通成员可阅读用途和流程，服务状态、历史部署摘要与账单导入仅管理员可用。

当前已有每轮独立 Python 子进程、私有临时目录、清理后的环境变量、私有 stdio、进程回收和 Node 权限门禁。Python 临时文件默认指向本轮私有目录，正常/故障收尾后随目录回收；容器部署还提供内存 / PID 限额。运行时不跨用户复用 Agent 对象、记忆或工具实例。

AgentScope Worker 执行可信 SDK，仍拥有同一系统用户权限。用户代码另通过 `integrations/agent-sandbox/` 的独立服务和 MCP 工具执行，首期限定 Python 3.12 源码与文本产物。每轮固定镜像 ID、非 root、禁网、只读根、无 IPC、私有工作盘及资源限额；不挂载应用目录、输入附件、Docker socket 或宿主凭据。

独立服务遵循以下契约：

1. **先限定任务**：首期只处理用户明确选择的文本 / 文件转换，定义允许语言、输入大小、运行时长、产物大小和失败语义。
2. **定义不可绕过的隔离**：一次任务一个临时容器或 microVM；非特权用户、只读根文件系统、临时工作盘、CPU / 内存 / PID / 时间限额。容器和 microVM 的隔离强度不同，应按威胁模型选择并验证。
3. **隔离数据与网络**：默认禁网；只挂载本轮批准输入，不挂载工作空间、Docker socket、宿主凭据或长期目录。需要网络时通过声明用途的出口代理和允许列表。
4. **保留治理链路**：提交与回收仍关联同一个 runId / stepId；写操作授权、幂等和取消不因为运行在沙箱就消失。取消后验证进程和工作盘回收，保留 unknown 状态处理远端副作用。
5. **验收产物**：产物有大小、类型、扫描、保留期和访问权限规则；先预览，再由用户选择下载或发布到外部系统。

`sandbox_execute_python` 是写工具，在执行中心批准固定源码与 runId/stepId 计划后才提交；查询工具按相同身份和标签读状态，真实 MCP SDK 取消通知传入服务。未确认容器清理时暂停后续执行并重试回收。文本产物先扫描，再由独立管理员预览并按同一摘要批准；提交人不能自批，下载再次核验。本机真实 Docker/SDK/应用审批验证见[验证记录](verification.md)，接入见[沙箱说明](../integrations/agent-sandbox/README.md)。Docker 共享宿主内核，生产需独立服务账户与目标平台隔离验收。

早期[隔离协议与威胁模型](../openspec/changes/agentscope-sandbox-protocol-20261008/design.md)及 `agent:sandbox:probe` 保留作单独容器合约探针。服务验收使用 `npm run sandbox:accept -- LOCAL_IMAGE --out NEW_REPORT.json`，文件名位于 `test-results/agentscope/`，覆盖实际执行、独立产物批准、超时/取消/清理及现有应用写审批；不代表内核逃逸或生产隔离已经验收。

## 从可用走向高水准：有先后顺序的路线

当前已具备资源授权 / 发布、持久执行与审批、真实 SDK 编排、知识检索、可选独立复核、问答全景、显式只读目标绑定和学习入口。下一阶段应优先减少错误动作、提高结果可证实程度，再增加自主性。以下条目中已交付切片与待验收目标分别说明。

| 优先级 | 建议能力 | 为什么先做 | 可以验收的结果 |
| --- | --- | --- | --- |
| P0 | 查询前的目标意图绑定 | 已知“换成另一个授权目标再回答”的问题不能只靠查询后的复核阻止 | 已有单工具、单对象结构化确认和调用前拒绝的合成回归；本机 DTS 策略已同步，下一步核对真实目标链路与歧义语料，并设计多工具诊断目标集合 |
| P0 | 真实质量评测与发布门禁 | 工具调用成功和模型答得正确是两个目标 | 用户已确认 DTS 样本为真实需求；来源、答复/证据/评分标准有逐条 AI 工程复核入口。保存模型实际失败、正式人审与真实质量门槛分别记录 |

问答全景后续可以分为三层：单次问答处理路径、资源与版本依赖、跨会话统计。它们应共享可核对的 ID，但不能把“资源已配置”混同为“本次已使用”，也不能从模型文字猜测出系统未记录的节点。遥测应默认最小化采集，问题正文、工具原文、密钥和个人数据不随 trace 自动输出。

本轮按用户选择完成本机部署与工具。后续门槛包括保存模型实际稳定响应与质量、正式发布人审、真实账单输入和生产隔离验收。工程复核、真实模型结果与生产批准分别报告；来源审核不运行模型，合成通过不能填补真实质量证据。

扩大自治范围的依据应是前一步的实际验收结果。先让用户能够判断“为什么这样做、做了什么、还缺什么”，再逐步开放代码、外部写入和多 Agent 自主协作。
