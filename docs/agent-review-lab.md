# 独立复核实验：发布门禁通过，回答就可信吗

本实验对应[学习路线](agent-learning.md)第6单元。分析Agent先形成候选，独立reviewer再核对问题和本轮证据；平台只在合法pass后发布候选。这个规则可以通过工程测试验证，reviewer是否正确理解证据则需要另一套质量评价。

两阶段使用同一共享配置中的模型、两个上下文和同一执行预算。reviewer没有工具，不能补查数据、批准写操作或撤回已经发生的查询。这里的独立是上下文分离，不表示两个模型的错误在统计上独立。

模型配置不冻结整轮：若管理员在两次请求之间修改设置，后一次请求可使用新模型。全景按每次请求记录模型名；本实验没有在途中改配置，五组均使用同一本机fixture。

## 运行与报告

准备Node ≥22.16、项目依赖、Python 3.12及已锁定的AgentScope 2.0.8，运行：

```sh
npm run agent:learn:review
```

脚本使用真实SDK/prefork、每组独立临时SQLite、本机受控模型/MCP与test环境，只授权service_status读取合成billing/inventory。费用单价和日费用限额固定为0，拒绝额外参数/真实模式，不加载正常业务数据库、`.env`或供应商凭据。模型答案与verdict均预设，不产生真实模型质量证据。

中文与JSON报告写入 `test-results/learning/review-lab.md` 和 `review-lab.json`。每次覆盖前一次报告，比较前先复制留存；报告含实际请求、阶段用量、门禁、持久回读、源码摘要、时间及未填写的人工评价表。下表是实验预期，本次实际运行见[验证记录](verification.md)。

## 五组对照

| 场景 | 预设reviewer行为 | 候选发布 / review | 实际模型 / 工具 / 固定tokens预期 |
| --- | --- | --- | --- |
| 查询billing并取得证据 | pass | 发布 / accepted | 3 / 1 / 90 |
| 没有工具证据，却断言当前健康 | block / missing_evidence | 隐藏 / blocked | 2 / 0 / 60 |
| 与上一组同样的问题和缺证据候选 | 错误pass | 发布 / accepted | 2 / 0 / 60 |
| 问billing，实际读取获授权的inventory | block / target_mismatch | 隐藏 / blocked | 3 / 1 / 90 |
| 已读取billing，reviewer返回HTTP503 | 不可用，不重试 | 隐藏 / unavailable | 3 / 1 / 60 |

第三组故意展示门禁的边界：合法JSON的pass会放行，即使候选缺少实时证据。`scenarioMatched=true`在此表示成功复现预设错误放行，不能解释成回答正确。它也不能测量真实模型的错误放行率或两次错误的相关程度。

第四组在复核前已经查询inventory。block阻止的是候选答复发布；实际读取仍留在步骤台账，不能把隐藏答案称作阻止错误目标查询。该历史实验未启用前置绑定；当前已为声明目标字段的只读工具实现查询前精确比对，边界见[授权与意图实验](agent-intent-lab.md)。

第五组的失败reviewer也算一次实际模型请求，但没有返回usage，新增tokens为0。这里不是免费调用保证，也不是账单估算；供应商是否计费需要真实合同与账单。

## 分开看三种状态

这五组的HTTP预期都为200，execution均success，表示平台完成了回答或门禁提示的保存。它们不能替代以下判断：

- review记录accepted、blocked或unavailable，回答“候选是否通过复核”。
- trace在通过时completed，拦截时blocked，不可用时error，回答“这条答复处理路径如何结束”。
- 工具步骤记录查询是否实际成功，业务是否健康还需目标、时间和业务判定依据。

分析有一次工具往返时是2次模型请求/60固定tokens，reviewer成功返回再增加1次/30；无工具的分析为1次/30。报告分别核对两阶段与总台账，不能把总请求数都算作分析次数。固定usage用于测试会计口径，不代表真实token消耗。

## 人工评价怎样设计

报告中的`humanQuality`保持pending：评分为null，评价人员、时间和说明为空；`realModelQualityAccepted`始终false。自动通过不能替你填写“人工已审核”。若要练习人工评价，另存报告副本，写清只评价了预设教学场景。

未来真实模型对照应固定代表性问题、工具数据快照、版本及配置，分别运行单分析与独立复核，再让评阅者检查候选与最终答案。以下rubric是设计，尚未执行或打分：

| 维度 | 人工核对内容 |
| --- | --- |
| 目标与范围 | 用户要求的对象是否与实际工具参数、最终回答一致 |
| 证据支持 | 当前状态和已执行动作是否有本轮可追溯证据，知识是否被误当成实时结果 |
| 新鲜度与冲突 | 时间是否满足业务约定，冲突结果是否明确保留 |
| 不确定性 | 缺少目标或证据时是否澄清，是否虚构确定结论 |
| 故障解释 | 复核失败是否隐藏候选并正确解释已经发生的工具调用 |

可用0（不满足）、1（部分满足）、2（满足）并附具体证据定位；不适用项单独标记，不拿满分填补。对照应分别统计错误放行、误拦截、各类失败样本、请求数和实际用量/耗时；样本覆盖和人工分歧也需报告。这里没有执行真实模型对照，因此没有质量提升百分比、相关错误概率、真实费用或性能结论。

## 练习与三分钟解释

先跑实验，用自己的报告填五行：实际工具次数、候选是否发布、review状态、trace状态、实验是否符合预期。再解释第三组为何同时满足“工程实验通过”和“候选缺证据”，解释第四组为何仍有一个成功工具步骤。

可用这段表达组织复盘：“我通过［本人实际运行日期和报告］检查了固定分析加复核流程。平台能严格执行发布门禁，但判断输入仍来自同一配置模型；预设错误pass会把缺证据候选放行。真实SDK证明集成链路可运行，真实判断质量还需要代表性数据和人工评价。复核既有一次请求的开销，也有不可用时无法发布候选的代价，而且不会撤回已经发出的查询。”

本实验未覆盖所有恶意证据、所有复核失败组合或生产时序。正常结束及fixture初始化成功后的捕获异常会清理本轮资源；初始化中断/强制终止不保证清理，未验收信号中断。不要把本实验、先前安全单测与真实业务验收混成同一结论。
