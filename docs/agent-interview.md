# Agent 面试与项目复盘：用证据讲清楚工程能力

这份材料配合 [Agent 学习路线](agent-learning.md) 使用。回答的重点是：系统解决什么问题，你理解或实现了哪部分，为什么选择这个方案，证据能支持什么结论。仓库已有功能不自动等于你的个人贡献；先区分「阅读理解」「复现实验」「亲自设计或实现」再写简历。

## 90 秒项目介绍模板

下面是可以改写的练习稿。方括号必须替换成你真实完成的内容，不要直接把项目全量能力当成自己主导的工作。

> 我用一个运维 Agent 工作空间学习并实践了 Agent 工程。它把知识资料、已发布的 Skill 和 MCP 工具接到对话里，目标是让一次查询或变更建议既能完成任务，也能追溯实际证据。
>
> 前端是 React，后端是 Express 和 SQLite；AgentScope 在 Python Worker 中编排模型与工具循环，Node 保留模型上下文、权限、预算和持久执行的控制权。模型生成工具请求后，后端还会检查 Schema、身份和业务范围。写操作保存固定计划进入审批，结果不明确时走只读对账，避免盲目重放。
>
> 我重点完成了［真实贡献或学习实验］。其中一个关键取舍是［例如：为什么写操作出错后保留 unknown］，我用［实际运行的测试/失败样本］验证了［具体行为］。项目还有可选的独立复核和执行全景，用来控制答复发布并观察实际链路。
>
> 当前是单实例系统；检索是 FTS5 与词项评分，没有向量检索或长期记忆。我的验证主要覆盖［本地 fixture / 真实 SDK / 实际运行的其他层级］，尚不能据此声称生产诊断准确率或复核收益。下一步我会针对［具体缺口］设计可复现评测。

如果你目前主要在学习，开头可以直接说「这是我用于 Agent 工程学习与实验的项目」。清楚解释一个亲自复现的失败路径，比没有证据的「全栈主导生产 Agent 平台」更有说服力。

## 10 组核心问答与追问

### 1. 这个项目为什么算 Agent？和普通问答或工作流有什么区别？

**回答要点。** 普通模型问答可以只完成一次生成；这里模型能根据当前上下文请求工具，执行结果再进入后续模型调用，形成受限的行动与观察循环。AgentScope 负责循环编排，Node 负责实际模型出口、权限与工具执行。固定 Runbook 则按发布的步骤和参数执行，不需要模型临时决定下一步。

不要把「用了框架」当成 Agent 的唯一标准。应指出决策发生在哪里、反馈如何改变后续请求，以及循环如何停止。

**源码与证据。** [runRuntime()](../server/agent-runtime/index.mjs)、[Worker main()](../agent-worker/worker.py)；[runtime.test.mjs](../tests/agentscope/runtime.test.mjs) 验证多轮工具反馈、批次顺序及六次实际模型调用上限。

**追问。** 框架到达迭代上限后又尝试总结怎么办？答：Node 对每次实际供应商调用计数和预留预算，框架内部行为不能绕过外壳限制。一次模型调用可包含多个工具，因此模型调用数与步骤数要分开统计。

### 2. 你怎样管理上下文？有没有长期记忆？

**回答要点。** 后端保存会话，但默认只读取最近 30 条 user/assistant 文本。可选预算模式按完整 user 轮次删除更早历史，保留系统规则与当前问题，记录省略提示；必需内容超限则明确失败。当轮原始工具消息和 Responses reasoning 不做这种裁剪。当前没有跨会话的长期记忆检索、自动摘要记忆或记忆写入策略。

预算使用 UTF-8 JSON 字节做保守估算，与实际 token 不完全相等。回答时应同时说出成本控制效果与估计误差，不把字节减少等同于供应商费用同比减少。

**源码与证据。** [prepareContext()](../server/agent-context.mjs)、[execute() 的历史查询](../server/agent.mjs)；[agent-enhancements.test.mjs](../tests/agent-enhancements.test.mjs) 验证完整轮次、必需输入超限和当轮工具/reasoning 保留。

**追问。** 被裁掉的历史里有任务 ID 怎么办？答：不能靠模型猜回 ID，应请求补充；若未来实现摘要或长期记忆，要另行解决来源、更新、冲突、撤权与删除问题。

可亲自运行[上下文与检索实验](agent-context-lab.md)：对照ID仍在数据库、从模型输入被省略、当前重新提供后恢复三个事实。省略提醒只是工程要求，受控模型不能证明真实模型必然追问；字节变化也不代表真实费用变化。

### 3. 你们的 RAG 是怎么做的？为什么没有向量数据库？

**回答要点。** 当前从有权限且符合绑定的知识资源中，使用中文二元词项和 SQLite FTS5 选候选，再按标题/描述/正文词项命中评分，返回带文档修订、版本和偏移的片段。可选多样性选择给不同文档留名额，避免长文档的重叠片段占满窗口。这属于检索增强流程，但不是 embedding 检索。

这套方案依赖少、容易本地复现，适合先把权限、版本与证据链讲清楚；同义表达和深层语义匹配能力有限。是否换向量库应由代表性检索语料、命中与引用质量决定，不能仅凭「Agent 必须配向量库」。

**源码与证据。** [indexKnowledge()](../server/governance.mjs)、[terms()/retrieve()](../server/retrieval.mjs)；[agent-enhancements.test.mjs](../tests/agent-enhancements.test.mjs) 和 [scenarios.test.mjs](../tests/scenarios.test.mjs)。

**追问。** 向量检索准确率更高是否就能上线？答：仍需验证权限过滤、过期文档、来源版本、引用与真实回答质量；当前仓库没有完成这种替换后的比较。

### 4. MCP 与 function calling 是什么关系？工具安全靠哪一层？

**回答要点。** 模型通过 function/tool calling 提出工具名和参数；Node 把模型别名映射到 MCP 暴露的工具，再通过 MCP SDK 执行。MCP 统一发现与调用协议，不替代业务授权。允许列表、工具策略、角色/用户、环境、参数范围和 Schema 在后端检查；调用前还要重新检查资源和身份，避免网络等待期间发生撤权。

模型提示中的「只读」「不要越权」有助于行为引导，但不是强制执行边界。工具包中的脚本也不会因为 Skill 被选择就自动执行。

**源码与证据。** [connectMcp()/discover()](../server/mcp.mjs)、[authorizeTool()](../server/governance.mjs)、[executeStep()](../server/execution.mjs)；[security.test.mjs](../tests/security.test.mjs) 与 [runtime.test.mjs](../tests/agentscope/runtime.test.mjs)。

**追问。** 参数在授权范围里，是否说明查询正确？答：不一定。模型可能把用户要求的对象替换成另一个允许对象；「允许执行」与「符合用户意图」需要分别检查。现有真实验收已记录过此类缺陷，不能宣称范围策略完全解决了它。

可复现证据见[授权与意图实验](agent-intent-lab.md)：固定billing请求，允许billing/inventory；选inventory仍会真实查询一次，越权payroll则0次。分别报告实验是否符合预期、是否满足本次目标。该实验运行时尚无前置绑定；当前已为声明 `requiredTargetFields` 的只读工具加入本轮结构化目标确认与调用前精确比对，现有 DTS 资源还需同步策略并做真实复验。事后精确比较不是生产意图识别器。

### 5. 工具调用怎样做到幂等？是 exactly-once 吗？

先运行[写入结果未知实验](agent-unknown-lab.md)，用自己的写请求数、实际应用次数和只读对账证据解释后面的取舍。

**回答要点。** 需要分三层说：请求层用用户 + requestKey 和输入摘要防重复受理；步骤层用 run 内调用身份和参数/版本摘要拒绝变造重传，并可返回持久结果；业务工具层用平台注入的幂等参数，由远端实现去重。平台自己的数据库去重不能单独保证跨网络 exactly-once。

相同键不同输入应冲突，不该复用错误结果；已经受理但结果未知，也不该再次发送写操作。远端是否真的遵守幂等键，需要独立验收。

**源码与证据。** [run()/callStep()](../server/execution.mjs)、[bridgeSession()](../server/agent-runtime/protocol.mjs)；[agent-runtime.test.mjs](../tests/agent-runtime.test.mjs) 验证并发/重启去重、持久加密返回和 unknown 不重放。

**追问。** 供应商连续两轮都返回同一个 call ID 会不会被误去重？答：Node 会把模型轮次纳入别名，持久步骤还结合 Worker reply ID；同一轮重传与不同轮合法调用不是同一身份。

### 6. 为什么有 unknown？用户取消了为什么还要核对远端？

**回答要点。** 写请求发送前失败与发送后未确认的性质不同。请求已发出时，即便超时、取消或返回错误，副作用也可能已发生；系统把这种结果保留为 unknown。随后用批准的只读核验检查目标状态，成功也不重放原写请求。取消终止后续工作、释放资源，不等于对远端事务执行回滚。

审批保存的是具体参数、资源版本与 Schema 摘要。执行时重新检查身份、权限、有效期及远程 Schema；它不是「审批过这个工具，以后任何参数都可以执行」。

**源码与证据。** [executeStep()/approve()/reconcile()/cancel()](../server/execution.mjs)；[execution.test.mjs](../tests/execution.test.mjs) 中先写入再返回错误、只读对账仍仅一次写调用的用例。

**追问。** 对账发现目标状态符合预期，能否证明一定是本次写入造成？答：不能，目标状态核验和因果归属不是一回事；更严格的工具合同可能需要操作 ID、版本、审计日志或业务事务记录。

### 7. 为什么用 Node + Python？prefork 算沙箱吗？

**回答要点。** Python 承载 AgentScope 编排，Node 复用现有认证、模型协议、数据与执行治理，避免两边各自实现权限和持久状态。cold 每次启动解释器；prefork 预加载 SDK，再为每轮 fork 新子进程，复用导入成本但不复用用户 Agent 和事件循环。代价是多了版本化管道协议、进程生命周期和资源回收的复杂度。

进程分离及凭据最小化不是通用代码沙箱。当前 Worker 跑可信 SDK，不支持用户任意脚本；文件系统和网络隔离还依赖操作系统/容器部署策略。

**源码与证据。** [Worker 地图](../agent-worker/codemap.md)、[createWorkerPool()](../server/agent-runtime/pool.mjs)；[pool.test.mjs](../tests/agentscope/pool.test.mjs)、[agent-pool-protocol.test.mjs](../tests/agent-pool-protocol.test.mjs)。

**追问。** Worker 崩溃能否自动换另一个引擎继续？答：本项目不这么做。工具可能已经有副作用，回退重跑可能重复执行；失败收尾与可核对的执行台账更重要。cold/prefork 是同 SDK 的部署模式，不是故障时自动重放路径。

### 8. 双 Agent 复核能提高准确率吗？

**回答要点。** 目前实现了可选的分析与独立证据复核：分析最多 5 次模型请求，reviewer 最多 1 次，两个上下文、同一共享配置中的模型（配置未在请求间变更时名称相同）、共享预算。reviewer 没有工具，输出必须满足严格 pass/block JSON；通过才发布候选，证据截断、预算不足或复核故障时不发布候选。待审批计划直接走人工流程。

能确认的是发布门禁、预算与权限行为已被 fixture 测试覆盖；不能仅凭这些测试断言真实准确率提高。应对比单分析与复核的错误放行、误拦截、延迟、用量和人工判断；同模型相关错误与提示注入风险仍然存在。

先运行[独立复核实验](agent-review-lab.md)：同一缺证据候选在预设block时隐藏，在预设错误pass时发布。后者的scenarioMatched=true表示反例如期出现，不表示质量通过；问错目标后block也不能抹去已完成的查询。人工rubric尚未打分，不将固定tokens或预设verdict包装成真实收益。

**源码与证据。** [reviewAnswer()/reviewText()](../server/agent-review.mjs)；[agent-review.test.mjs](../tests/agent-review.test.mjs)、[agent-review-security.test.mjs](../tests/agent-review-security.test.mjs)。

**追问。** 为什么复核不再查一次工具？答：当前选择固定的一次证据检查，限制额外副作用、范围扩张和成本。它因此无法主动补齐缺失证据，也无法撤销分析阶段已经发生的查询。这是明确取舍，不是完备防线。

### 9. 如何调试 Agent？把思维链打印出来吗？

**回答要点。** 调试首先需要实际发生的上下文选择、模型请求、工具步骤、复核与完成事实。执行全景记录受控摘要、资源身份、依赖、耗时和用量，通过 NDJSON 发送并保存在消息 metadata；不采集问题/提示原文、完整工具参数/返回正文或私有推理。需要参数级调查时走受权限保护的执行记录。

普通聊天的正文增量走上游 SSE → Node → NDJSON → UI；进度流与文本流是两件事。复核模式禁止提前流出草稿；截断流不保存成完整回答，最终通过持久回读收敛。

**源码与证据。** [createExecutionTrace()](../server/agent-trace.mjs)、[readModelStream()](../server/model-stream.mjs)；[agent-trace.test.mjs](../tests/agent-trace.test.mjs)、[chat-stream.test.mjs](../tests/chat-stream.test.mjs)。

**追问。** trace completed 能否当作业务成功率指标？答：不能。它表示答复流程完成，里面仍可能有工具发现失败等数据源缺口；业务健康必须由相应证据与判定规则确认。实际工具执行报错会中止本轮；复核拦截时 trace 总状态为 blocked，复核不可用为 error，不能混称 completed。执行台账有自己的状态语义，历史快照也不覆盖之后的人工审批状态。

### 10. 你怎么评测，如何决定是否上线？

**回答要点。** 分开看工程协议、真实模型行为、业务数据和生产条件。fixture 适合可重复故障和门禁断言；真实 SDK 验证框架兼容性；代表性真实模型语料加人工审核才涉及诊断与拒绝质量；目标环境压测、权限、工具合同与运维验收另有要求。报告必须绑定源码、语料、配置和评测时间，避免拿旧候选的好结果证明新版本。

当前 `agent:eval` 默认只是小规模本地 fixture 工具选择回归。DTS 验收器检查完整报告与人工复核；即使评测门槛满足，也不自动批准生产上线。最新可宣称的证据应回看 [验证记录](verification.md)，不要混用不同时期的测试数量和真实性等级。

**源码与证据。** [evaluate-agent-runtime.mjs](../scripts/evaluate-agent-runtime.mjs)、[assessAcceptance()](../scripts/agent-acceptance.mjs)；[agent-acceptance.test.mjs](../tests/agent-acceptance.test.mjs)。

**追问。** 固定模型下 prefork P95 更低，可以写「生产性能提升」吗？答：只能描述这次环境、样本与协议下的测量；真实供应商延迟、并发、资源争用和流量分布可能改变结论，不能外推生产比例。

## 两个可深入讲的工程取舍案例

### 案例一：写入结果不确定时，放弃自动重试

**问题。** 远端已经改变状态，却返回失败或中断连接。把所有失败都当成「未执行」会导致重复写入；把本地取消当成回滚也会误导操作者。

**选择与代价。** `executeStep()` 用请求是否已经发出区分失败；对于已发出的写操作，未确认结果保留 `unknown`。`reconcile()` 只读查询批准的核验目标，确认后更新台账，不重放写操作。代价是牺牲一部分自动恢复便利，需要对账或人工接管；核验只能确认合同定义的目标状态，不能推导远端完整事务因果。

**证据与复现。**

```sh
node --test --test-name-pattern='ambiguous write outcome' tests/execution.test.mjs
```

读 [测试](../tests/execution.test.mjs) 和 [执行器](../server/execution.mjs)：fixture 先更新内存状态再返回错误，执行为 unknown；只读对账确认 maintenance，写调用计数仍为 1。其他未匹配测试被跳过是本命令的预期行为。

**面试表述。** 「这个案例让我把 HTTP 失败、操作失败和结果未知分开。我的证据是［本人实际运行结果］。如果接企业工具，我还要验收远端幂等键与核验接口合同。」若你没有实现过此功能，把「我设计」改为「我通过源码与实验理解」。

### 案例二：独立复核采用发布门禁，接受延迟与不可用成本

**问题。** 用户如果先看到分析草稿，即使 reviewer 最后 block，错误结论也已经泄露。证据不全时强行缩短输入以获得 pass，还可能把复核变成形式上的确认。

**选择与代价。** 复核模式关闭分析/reviewer 正文增量，只有 accepted 才发布候选；严格解析结果，证据截断和预算不足时不发送不完整证据。代价是用户等待最终答复更久，多一次模型调用，而且模型或预算故障会降低答复可用性。它控制的是发布行为，不能撤销之前的工具读取，也不能保证模型判断正确。

**证据与复现。**

```sh
node --test tests/agent-review.test.mjs tests/chat-stream.test.mjs
```

读 [reviewAnswer()](../server/agent-review.mjs)、[复核测试](../tests/agent-review.test.mjs) 和 [流式测试](../tests/chat-stream.test.mjs)：检查 malformed verdict、target mismatch、预算不足、截断证据和 pass/block 两种流式门禁。预设 pass/block 的 fixture 证明门禁实现，不证明真实模型复核准确率。

**面试表述。** 「我会把功能正确性与质量收益分开验收。先验证草稿不泄露、失败不默认放行；再准备真实模型对照和人工标签，估计错误放行与误拦截的变化。」

## 简历描述模板与贡献核对

先选与你实际经历相符的一档，再替换方括号。没有真实测量就不要加百分比；本地测试数量也不要改写为线上吞吐或准确率。

| 实际经历 | 可改写描述 |
| --- | --- |
| 阅读并复现 | 基于 React / Express / SQLite / AgentScope 运维 Agent 项目开展源码学习，复现［具体测试］，梳理工具授权、审批、幂等与未知结果对账链路，完成［个人复盘产物］。 |
| 亲自实现一项变更 | 在运维 Agent 项目中实现［明确模块/行为］，处理［触发条件或故障］，补充［实际测试与文档］；在［验证环境］确认［可观察结果］。 |
| 亲自负责评测 | 设计并运行［代表性语料/故障注入实验］，固定［源码/配置/数据版本］，按［实际指标］比较［候选方案］，记录失败样本与未验证边界。 |

提交简历前，逐句回答四个问题：这是不是我做的？我能指出相关代码吗？我亲自运行过哪项验证？这个数字或结论是否超出了证据？未完成的工作写成「计划」或不写，已有系统能力不要统一写成个人主导。

## 一次 30 分钟的自测

先用 2 分钟讲介绍，再用 8 分钟解释一次含工具调用的请求；用 10 分钟讲上述两个取舍案例，最后用 10 分钟回答反例：工具获授权但对象错了、写入后断网、历史任务 ID 被裁剪、reviewer 故障、trace completed 但业务数据过期。

每题按四项自查：能讲概念、能定位函数、能解释测试断言、能说明局限。任何一项说不清就回到 [对应学习单元](agent-learning.md)，补一次实验和自己的解释，再录一遍。目标是形成可追溯的工程判断，不是背出所有术语。

## 观测实验追问

运行[可观测性实验](agent-trace-lab.md)后，分别解释：模型请求1次但run失败为何仍有用量；工具步骤success但degraded为何不矛盾；trace.finishedAt为何不能替代业务reportedAt。给出自己实际报告中的节点/run/step与时间，区分本机等待注入、真实供应商性能和未取得的账单，不虚构优化收益。
