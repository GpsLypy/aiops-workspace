# ReAct 实验：看见一次工具往返如何发生与停止

本实验对应[学习路线](agent-learning.md)的第 1 单元。目标是把「模型请求调用」「执行器真的调用」「工具结果进入下一次模型请求」分成三件能核对的事实，再观察坏参数与循环上限如何让它停止。

实验使用真实 AgentScope 2.0.8、当前 Node 治理链路、临时 SQLite 和本机 HTTP 模型/MCP fixture。模型的选择由脚本预设，工具读取合成的 `billing` 状态；不是模型自主推理效果、生产状态或诊断质量评测。

## 一条命令，得到自己的证据

先按[运行指南](agentscope-runtime.md)准备 Node ≥22.16、Python 3.12、uv 和锁定依赖。然后在仓库根目录运行：

```sh
npm run agent:check
npm run agent:learn:react
```

实验生成两个本地报告：`test-results/learning/react-lab.md` 用于阅读，`test-results/learning/react-lab.json` 用于逐项核对。报告包含运行时间、实际 Worker 模式、固定源码清单的 SHA256、每场景的预期与实测，以及按模型请求顺序的观测。再次执行会更新这两个文件；要比较两次结果，先保留自己的报告副本。

脚本不接受额外参数，也没有 `--real` 模式，不加载 `.env`，不使用正常业务数据库或已保存的模型配置。它只开放本地 `service_status` 只读工具，fixture 内的 `production` 是用来测试权限的环境标签。正常结束及场景初始化成功后的捕获异常会关闭本机服务、Worker并清理临时数据库；初始化中断或强制退出不保证清理，未做信号中断验收。报告留在 Git 忽略的 `test-results/`。

本地fixture的 `MODEL_PRICE_PER_MILLION` 与 `DAILY_COST_LIMIT` 都固定为0，不继承宿主的真实费用限额。这样不会因“零单价与非零限额”配置冲突在模型请求前误报503；固定token数字仍只用于核对台账，不代表真实费用。

## 先预测三个场景

下面是验收预期，不是你的运行结果。请先遮住实测报告，预测每列，再运行命令比较。

| 场景 | 模型 HTTP 请求 | 实际 MCP 调用 | 持久工具步骤 | HTTP / 执行状态 | 关键现象 |
| --- | --- | --- | --- | --- | --- |
| 正常工具往返 | 2 | 1 | 1 个 success | 200 / success | 第二次模型输入已经含 1 条工具结果 |
| 非法 JSON 参数 | 1 | 0 | 0 | 502 / failed | 参数未过校验，不会变成一次真实工具执行 |
| 持续请求工具 | 6 | 6 | 6 个 success | 422 / failed | 第六次工具已经执行，但没有第七次模型请求消费其结果 |

每次受控模型响应声明 30 tokens，所以预期用量分别为 60、30、180。这是 fixture 固定值，仅用于核对累计行为，不是供应商计费或成本测量。不要把两个 HTTP 状态为错误的预期场景当成实验失败：是否通过应看实测与预期是否一致。真正不符合预期时脚本返回非零退出码，并在报告中记录失败。

## 沿正常场景逐步读报告

1. **第一次模型请求**：输入中没有 `tool` 消息，实际 MCP 调用数为 0。受控模型返回一个 `mcp_0` 工具请求。
2. **授权与执行**：Node 将 `mcp_0` 映射到本轮授权的 `service_status`，校验原始 JSON、Schema、用户、资源版本与参数策略，建立持久步骤后执行本地 MCP。
3. **结果回填**：工具请求消息和匹配的 `role=tool` 结果追加到 Node 保管的消息中，Worker 得到执行反馈。
4. **第二次模型请求**：报告中工具结果数变成 1，实际 MCP 调用数也变成 1。受控模型这次返回终态文本，执行台账记录 success。

这里的顺序来自模型服务收到的请求和实际工具/执行台账。报告不采集提示词原文、工具正文或私有推理，不能把它称为“模型思维链”。它也没有逐毫秒追踪 SDK 内部事件；两次模型请求之间发生的调用，通过计数与持久步骤相互核对。

## 两个失败路径为什么值得讲

**非法参数：模型提议不是执行事实。** 受控回复给出带尾随逗号的 JSON。运行时保留原始参数，不让 SDK 的修复结果绕过校验。此时模型已经调用一次、产生了固定用量，但没有 MCP 调用，也没有成功步骤。面试时应分别描述模型出口、参数校验、真实执行这几个位置。

**循环上限：模型请求数不是工具步骤数。** 此场景每轮恰好请求一个工具，所以最后两者都是 6。但一般情况下，一次模型响应可以包含多个工具；[已有 runtime 回归](../tests/agentscope/runtime.test.mjs)另外覆盖三次模型请求产生四个步骤。不能把“六次模型上限”说成“任何情况下最多六个工具”。

第六次请求返回的工具在当前实现里仍会执行，随后继续请求模型时被 Node 上限拒绝。于是“run failed”和“已有六个 success 步骤”可以同时成立。不能因整轮失败就宣称没有任何动作，也不能因为各步骤成功就声称拿到了最终答复。这个教学场景只读，因此不会涉及写入补偿。

## 三分钟面试复述与自测

按下面顺序用自己的话复述：

- 用 30 秒解释角色：模型提出动作，AgentScope 组织循环，Node 保留授权和持久执行权。
- 用 60 秒结合正常报告，指出第一次请求、真实工具步骤、第二次输入中 tool 结果的对应关系。
- 用 60 秒解释非法 JSON 与第六次上限：分别在哪个阶段停止，已有动作是否需要保留，为什么 SDK 的 max_iters 不能替代 Node 的实际调用计数。
- 用 30 秒限定证据：这次实验证明受控输入下的桥接和门禁行为，真实模型是否选对工具、是否给出正确诊断，需要另外的数据集和人工评价。

完成后留下这五项：运行时间、实际 Worker 模式、三个场景实测计数、一个说错后修正的理解、尚未验证的边界。若没亲自运行，可以说“阅读了实验”，不能把仓库报告当作自己的测试经历。

继续练习：为什么第六次工具结果没有被模型消费？一次请求两个工具时，哪些计数会变化？工具待审批时为什么不能把计划算作执行？后两个问题可以继续读已有 runtime 测试，本脚本没有覆盖审批、写入、取消、并发或真实供应商。
