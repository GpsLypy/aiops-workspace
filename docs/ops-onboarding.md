# 从零接入自己的运维系统：完整实操教程

这是一份可以跟着操作的课程：先用教学服务跑通知识库、Skill、MCP 和子领域的组合，再把数据源换成你自己的监控、日志或业务系统。完成后，你应能独立搭建一个“查手册 → 查当前状态 → 按规范分析 → 保存证据 → 定时巡检”的运维助手。

依据：[2026-09-20 全流程验收报告](verification.md)及当前仓库实现。报告已经验证真实模型与本机教学 MCP 的完整链路，尚未验证企业生产 MCP、生产写操作和企业身份联调。本教程新增的练习使用 `LAB` 名称与独立的示例文件，不依赖验收人员电脑上的 `test-results/`，也不需要覆盖原来的 `E2E0920` 资源。后续复测结果以验证记录为准。

## 课程路线与最后要交付的东西

| 阶段 | 你将做什么 | 完成标志 |
| --- | --- | --- |
| 第一课 | 分清五个组成部分 | 知道一段内容应该放哪里 |
| 第二课 | 准备环境和模型 | 登录、保存模型、普通对话成功 |
| 第三至六课 | 建知识、发布 Skill、接 MCP、建子领域 | 四类资源能在同一对话协作 |
| 第七至八课 | 做成功和失败对照实验 | 能证明数据来自哪里、权限是否有效 |
| 第九课 | 配置巡检任务 | 有独立会话与运行记录 |
| 第十至十一课 | 换成自己的系统，设计领域与授权 | 用真实只读数据完成一次业务验收 |
| 第十二至十四课 | 了解变更、排错与交接 | 知道扩展顺序、当前限制和验收条件 |

零基础使用者先完成前九课；编写系统接口的开发人员重点看第十课；运维负责人负责阈值、权限、发布和最终业务确认。一个人可以承担多个角色，但真实生产变更的双人审批仍需两个不同的管理员账号。

最后留下一份接入清单：**一个业务场景、一份真实手册、一个已发布 Skill、一个获准的只读工具、一个已发布子领域、一组验收证据和一个先暂停的巡检任务。** 先把一个场景做完整，再增加系统。

## 第一课：知识、方法、工具和子领域怎样组合

### 用“计费服务变慢”理解各自的工作

| 组成部分 | 回答什么问题 | 放什么内容 | 不负责什么 |
| --- | --- | --- | --- |
| 模型 | 如何理解问题、组织回答、提出工具调用 | Base URL、模型 ID、API Key | 不会自动知道你公司的状态或密码 |
| 知识库 | 有什么已知依据 | 服务说明、阈值、故障手册、业务约定 | 不会自动变成实时监控 |
| Skill | 应按什么步骤处理 | 先确认目标、收集证据、对照阈值、输出格式 | 不执行 ZIP 中的脚本，也不授予工具权限 |
| MCP | 怎样取得实时事实或执行获准操作 | 工具名称、参数定义、远程实现 | 协议本身不内置监控数据 |
| 子领域 Agent | 本次负责什么、能用哪组资源 | 职责指令及知识 / Skill / MCP 绑定 | 不会自动选择领域、启动多个助手或委派任务 |
| 定时任务 | 什么时候再做一遍 | 完整指令、处理 Agent、时间与时区 | 不继承之前聊天的上下文 |

模型可以理解为分析人员，知识库是手册，Skill 是作业规程，MCP 工具是查询窗口，子领域是这次工作的职责与资料范围。真正检查权限、调用工具和保存结果的是应用后端。

一轮组合的顺序是：用户选择子领域并提问；后端取出当前用户有权使用的绑定资源；检索知识片段、加载已发布 Skill、提供获准工具定义；模型提出具体查询；后端再次检查权限与参数并调用 MCP；模型结合返回值和手册生成回答；系统保存来源、工具摘要与会话。

### 一条规则应该写在哪里

| 想表达的内容 | 应该放在哪里 | 原因 |
| --- | --- | --- |
| “计费 P95 超过 800 ms 需要排查” | 知识库 | 这是需要维护版本的业务依据 |
| “先确认服务和环境，再查状态” | Skill | 这是可复用的方法 |
| “当前 P95 是 1260 ms” | MCP 返回值 | 这是有采样时间的观测数据 |
| “本助手只负责计费测试环境” | 子领域职责、资源绑定及工具策略 | 职责引导回答，绑定和策略限制能力 |
| “普通成员只能查询 billing-lab/test” | 资源读者权限、工具策略、远程账号权限 | 权限必须由程序执行检查 |
| “每天早上 9 点巡检” | 定时任务 | 这是触发计划 |

不要把访问令牌放进手册或 Skill；不要把实时值写死在 Skill；不要期待写一句“禁止操作其他系统”就完成权限隔离。子领域的“领域 / 标识”标签不等于绑定，资源的“服务标识”和“目标环境”也不是知识检索的自动隔离条件。当前知识检索主要按可见性、启用状态、子领域绑定、有效期与关键词筛选；测试 / 生产资料需要用明确绑定和权限分开。

### 四种常见组合

| 组合 | 适合做什么 | 能得到什么 |
| --- | --- | --- |
| 知识库 | 查询手册、解释指标 | 有依据的资料回答 |
| 知识库 + Skill | 标准化排障建议 | 按团队格式组织的回答 |
| MCP + Skill | 查询状态并整理巡检结果 | 有时间、目标和来源的观测事实 |
| 子领域绑定知识 + Skill + MCP | 围绕一个系统完整排障 | 有依据、有流程、有工具证据的分析 |

并非必须一次配齐所有组件；但“现在系统是否正常”必须有足够新鲜的实际数据。没有工具返回时只能解释手册、分析你提供的日志，不能宣称已经查过系统。

## 第二课：准备一套可练习的环境

### 需要准备什么

| 项目 | 谁提供 | 本课程用法 |
| --- | --- | --- |
| 本仓库源码、Node.js ≥ 22.16、npm、Python 3.12、uv | 环境维护人员 | 启动工作空间和教学 MCP |
| 一个管理员账号 | 首次初始化或现有管理员 | 建资源、配置模型、发布指令 |
| 兼容 Responses API 且支持工具调用的模型 | 模型服务提供方 | 普通问答及 MCP 工具调用 |
| Base URL、模型 ID、按需 API Key | 模型服务提供方 | 填入模型设置 |
| ZIP 打包工具 | 系统自带压缩工具或 `zip` | 打包 Skill |

普通模型连接测试只验证文本请求；工具调用兼容性要到第五、七课实际验证。已有正常环境时直接复用，不重新初始化账号或清空数据。

从仓库根目录运行，下面所有路径都相对于该目录：

```sh
node --version
npm ci
uv sync --project agent-worker --frozen
npm run agent:check
npm run dev
```

打开终端显示的前端地址，通常为 `http://localhost:5173`，被占用时可能是 5174。API 默认在 `http://127.0.0.1:3001`；访问 `/api/health` 应得到 `{"ok":true}`。首次创建管理员，密码至少 12 字符；已有账号就登录。完整安装说明见[启动与操作](getting-started.md)。

进入“工作空间设置 → 模型服务”，填入 API 前缀、模型 ID 和 API Key，先保存，再点“测试已保存配置”。API 前缀通常类似 `https://你的模型服务/v1`，不要填到完整 `/responses`。模型不接受 temperature 时，将 Temperature 留空。新建对话发送“请用一句话说明你能如何协助运维”，确认有真正的模型回复。

## 第三课：建立知识库，让回答有依据

进入“知识库管理 → 新建知识库”，按下表填写：

| 字段 | 练习值 |
| --- | --- |
| 名称 | `LAB 计费超时手册` |
| 描述 | `billing-lab 测试环境的 P95、连接池等待阈值与排查顺序` |
| 服务标识 | `billing-lab` |
| 目标环境 | 测试（`test`） |
| 领域 / 标识 | `billing-lab` |
| 文档版本 | `lab-1.0` |
| 使用范围 | 私有，先由自己完成练习 |
| 状态 | 已启用 |
| 有效期、来源 URL | 练习可留空；真实资料按维护制度填写 |
| Markdown 正文 | 导入练习包的 `knowledge.md` |

保存后打开详情，核对正文，再刷新页面确认还在。本项目中，一条“知识库”资源是一份 Markdown 正文，不是自动解析整个目录或一批 PDF 的文档平台。

新建对话，开启“知识库检索”，发送：

```text
billing-lab 测试环境的计费超时手册中，P95 和连接池等待数的阈值是什么？
请标注知识来源；如果提供了知识核验码也列出来。本次不要查询实时状态。
```

期望看到 `800 ms`、`20`、知识来源和手册中的核验码。不要把答案或核验码直接写入问题，否则无法判断模型是否读取了资料。通用对话可能同时检索其他可用资料；第六课会用子领域把范围固定到本课程资源。

维护真实手册时，每份资料至少写清适用服务与环境、指标单位与统计窗口、阈值、排查顺序、已知例外、维护人和版本。每个重要小节重复说明适用对象：当前检索最多返回五个片段，不会把整份长文都交给模型。

**本课验收：** 刷新后资料仍存在；答案来自知识正文；显示正确来源。来源徽标证明片段被提供给模型，不保证回答中的每句话都经过核验。

## 第四课：上传并发布 Skill，让处理过程可复用

练习 Skill 的核心规则是：确认服务与环境，读取手册，按需查询 `service_status`，把指标与阈值比较，按“观察事实 / 阈值对照 / 排查建议 / 来源与缺口”四部分回答。工具失败时明确缺数据；模拟数据明确标记；不执行写操作。

### 打包和上传

在仓库根目录运行：

```sh
cd docs/examples/ops-onboarding
zip -r billing-diagnosis.zip billing-diagnosis
cd ../../..
```

没有 `zip` 命令时，用系统压缩工具压缩 `billing-diagnosis` 文件夹。解压预览应只有一层技能目录，其结构是：

```text
billing-diagnosis/
  SKILL.md
  references/
    notes.md
```

不要把整个 `ops-onboarding` 文件夹再套一层打进去。ZIP 最多 600,000 字节，根目录或单层文件夹内必须恰好有一个 `SKILL.md`；更多限制见[入门操作](getting-started.md)。

进入“Skill技能 → 上传 Skill”，选择 ZIP。核对自动识别的名称 `billing-lab-diagnosis`、描述、版本 `1.0.0`、正文和两个文件；名称可以改为 `LAB 计费只读排障` 后提交。上传不会把它安装为本机脚本，也不会自动读取 `references/notes.md`。必要规则必须放在 `SKILL.md`，需要检索的长资料放在知识库。

### 这一步必须做：发布

上传后的 ZIP Skill **始终为草稿，包括管理员上传**。进入“详情 → 版本历史与发布 → 审核并发布已保存版本”，核对详情显示“已发布”。“已启用”是开关，“已发布”是审核状态，必须同时满足。

可在发布前后分别新建独立对话，询问：

```text
请按已加载的计费只读排障流程，列出 billing-lab/test 超时问题的检查顺序。
若存在流程核验码请列出；未加载相应流程就直接说明。
```

发布后应使用四段结构，出现 Skill 中的流程核验码。只看格式还不足以确认 Skill 生效，因为模型也可能自行使用相同标题；结合发布状态和核验码判断。若有其他同类 Skill，先完成下一课的子领域隔离再做对照。

更新 ZIP 内容时需要重新上传替换并保存、重新发布。文件内 `metadata.version` 是作者声明的展示版本，资源 `revision` 是系统的保存 / 发布修订，两者不同。当前没有自动语义版本升级、同名去重或生产 / 测试双槽位。修改正在使用的已发布 Skill 会先使它成为草稿。

**本课验收：** 能打开已保存 ZIP、查看文件、下载原包；明确看见发布状态；新对话按 Skill 工作。下载原包完整不代表其中的附件已进入模型上下文。

## 第五课：接上 MCP，让助手可以查状态

### 先运行一个可控的教学服务

另开一个终端，进入同一仓库根目录：

```sh
node docs/examples/ops-onboarding/mcp-demo.mjs
```

终端应显示 `http://127.0.0.1:43128/mcp`。保持这个终端运行，再检查健康接口：

```sh
curl http://127.0.0.1:43128/health
```

应返回 `{"ok":true,"fixture":true}`。直接用浏览器打开 `/mcp` 可能返回 405，这是该示例没有提供 GET 流的正常行为；连接测试应使用工作空间的“连接并发现工具”。

该服务只监听本机，提供两个工具：`service_status` 返回固定教学指标；`unapproved_probe` 是授权对照用的无副作用工具，保持不授权。成功查询时终端输出 `tool.call` JSON，作为独立执行证据。按 Ctrl+C 停止服务。

端口占用时不要停止不明进程，可以另选端口，例如：

```sh
TUTORIAL_MCP_PORT=43129 node docs/examples/ops-onboarding/mcp-demo.mjs
```

随后同步修改工作空间的 MCP 地址。这里的 `127.0.0.1` 是**应用后端所在环境**的本机地址。后端在 Docker、另一台服务器或远程开发机时，不能用它指向你笔记本上的 MCP；应部署可从后端访问的 MCP，使用对应 DNS / 地址和鉴权。

### 在工作空间配置服务、工具和策略

管理员进入“MCP服务 → 添加服务”：名称 `LAB 计费状态查询`，服务标识 `billing-lab`，目标环境“测试”，地址 `http://127.0.0.1:43128/mcp`，状态“已启用”，使用范围先“私有”。本机教学服务没有鉴权，Bearer Token 留空。

先保存，再打开详情点“连接并发现工具”。勾选 **`service_status` 一个工具**，不勾选 `unapproved_probe`。在“工具风险与范围策略（JSON）”粘贴以下完整对象，再保存：

```json
{
  "service_status": {
    "risk": "read",
    "roles": ["admin", "member"],
    "userIds": [],
    "environments": ["test"],
    "constraints": {
      "service": ["billing-lab"],
      "environment": ["test"]
    },
    "maxItems": 1
  }
}
```

| 配置 | 含义 |
| --- | --- |
| 勾选允许工具 | `allowedTools` 中包含真实工具名 |
| `risk: read` | 按只读流程执行；仍需确认远程实现真的只读 |
| `roles` | 允许的工作空间角色 |
| `userIds: []` | 不额外限制到指定用户 ID；资源 ACL 和角色检查仍生效 |
| `environments` | 允许的执行环境；聊天使用 MCP 资源所配置的环境 |
| `constraints` | 约束工具参数中指定顶层字段的精确值，也要求字段存在 |
| `maxItems` | 限制参数中嵌套数组的元素总数，不是单次查询条数或数字参数上限 |

“目标环境”与工具参数 `environment` 是不同层面的值，所以示例同时限制两者。不要只把资源表单改成“测试”，却让工具参数仍指向生产。远程接口也必须校验服务和环境；教程 MCP 自身有第二道范围检查。

“查看工具清单”展示的是已保存配置，不是在线探测，也不表示当前用户一定可以调用。发现成功、加入允许列表、策略匹配、实际执行成功是四个不同的检查点。

### 先做一次确定参数的工具测试

打开“执行与审批 → 提交确定的工具操作”，选择该 MCP、`service_status`、目标环境“测试”，参数填写：

```json
{"service":"billing-lab","environment":"test"}
```

提交后应看到执行记录，返回 `p95_ms=1260`、`connection_pool_waiting=37`、`fixture=true`、采样时间和窗口。本机 MCP 终端应新增一条 `tool.call`。这是直接验证工具链，尚未验证模型会正确提出工具请求。

**本课验收：** 能发现工具；只授权一个；策略成功保存；执行中心和 MCP 端记录对应同一个服务与环境。

## 第六课：用子领域把本次工作需要的资源组合起来

进入“子领域Agent → 创建子领域”，名称 `LAB 计费测试排障`，状态“已启用”，服务标识 `billing-lab`，环境“测试”，使用范围先“私有”。正文可以使用：

```text
你负责 billing-lab 的 test 环境只读排障。
使用绑定的手册解释阈值，遵循绑定的计费排障 Skill。
需要当前状态时使用绑定 MCP 中已获准的 service_status。
清楚区分教学模拟数据、已观察事实和待验证假设。
目标信息不足或资源不可用时，说明缺口；不要编造结果。
涉及其他服务或环境时，提示用户选择对应的子领域和授权资源。
```

分别勾选：知识库 `LAB 计费超时手册`、Skill `LAB 计费只读排障`（若未改名则为 `billing-lab-diagnosis`）、MCP `LAB 计费状态查询`。不要把同名旧验收资源一起选上。

管理员首次创建子领域时当前实现直接发布；成员创建、任何人编辑已有子领域后则为草稿。保存后检查详情，必要时展开“版本历史与发布”重新发布。绑定一个仍是草稿的 Skill 不会使它自动生效。

### 必须理解的资源规则

- **通用 Agent：** 使用当前用户可读、启用、满足发布条件的资源；会加载全部符合条件的 Skill，没有按名称自动挑选最适合 Skill 的步骤。
- **子领域：** 在上述集合中再取绑定 ID 的交集。知识仍需检索命中，工具仍需通过允许列表和策略。
- **某类绑定为空：** 不使用该类资源。只绑定 MCP、不绑定知识，表示只给它工具，不会自动补上通用知识。
- **共享子领域：** 不会自动共享绑定资源。普通成员需要同时能读取子领域、知识、Skill、MCP，且满足工具策略。
- **现有会话：** 子领域固定，切换要新建对话。后续轮次读取资源当前状态和内容，不把创建时版本永久冻结。

如果希望演练后再开放给同事，可以在每项资源的“指定可用用户与管理人”中添加读者，最后用该成员账号验证。管理员有更广的权限，管理员成功不能证明普通成员也被正确授权。

**本课验收：** 三类绑定正确、Skill 和子领域已发布，且你能解释“空绑定”与“默认全部可用”的区别。

## 第七课：完成第一次组合排障

回到前台，新建对话，**发送前选择 `LAB 计费测试排障`**，开启知识检索。发送：

```text
请排查 billing-lab 的 test 环境计费超时问题。
调用 service_status 获取本次状态，再对照已绑定手册中的 P95 与连接池等待数阈值。
按已加载的排障流程输出，区分观察事实、假设和建议；注明采样时间与统计窗口。
如果资料或工具中有教学核验码，请按来源列出。工具未返回就明确说明，不能补造数据。
```

正常情况下应该得到：

| 证据 | 预期值 | 证明什么 |
| --- | --- | --- |
| 知识来源 | `LAB 计费超时手册`，阈值 800 ms / 20 | 提供了绑定知识 |
| 知识核验码 | `KB-LOTUS-2048` | 读取到知识内容 |
| 四段结构及流程核验码 | `SKILL-PINE-4096` | 已加载 Skill 的流程要求 |
| 工具摘要 | `LAB 计费状态查询 / service_status` 成功 | 应用实际走过工具执行 |
| MCP 终端记录 | service=billing-lab，environment=test | 工具端收到正确目标 |
| 指标与工具核验码 | 1260 ms / 37，`MCP-MAPLE-8192` | 取得教学 MCP 返回 |
| 数据性质 | 明确写教学模拟，fixture=true | 没把练习当生产事实 |

阈值差值应为 `1260 - 800 = 460 ms`、`37 - 20 = 17`。这只能说明两项教学指标超阈值，不能据此断言“数据库一定是根因”。合理建议是继续查询慢查询、连接占用、下游耗时和发布变化；本示例没有这些工具，助手应说明证据缺口。

再在同一会话追问：

```text
仅根据上一轮结果，两项指标分别超过阈值多少？不要重新查询。
```

期望正确计算差值，不新增工具调用。随后若想了解当前状态，需要明确要求重新查询：旧会话中的观测值只能代表当时。系统每轮仅读取最近 30 条 user / assistant 消息，不会永久记住全部历史，也不会跨新会话自动记忆。

**本课验收：** 三种核验码、正确来源、成功工具摘要和服务端调用记录相互印证。自然语言答案不是执行凭证；文字中写“已查询”而没有对应证据时，应继续排查。

## 第八课：做五组对照，确认它真的按配置工作

先保存成功会话，再逐项用新会话做实验；不要在新问题里复制之前的结果或核验码，以免干扰判断。这些检查是复测步骤，不表示当前环境已经自动通过。

### 对照一：关闭知识，仅分析附件

新建对话并选择原子领域，关闭“知识库检索”，导入练习 `incident.log`。发送：“只分析附件中的请求号和超时次数，不调用工具。若未提供知识资料，不要补充知识阈值或核验码。”

期望得到请求号 `ATTACH-IRIS-1024`、超时 3 次，没有知识来源。关闭知识不会关闭 Skill 或 MCP；“不调用工具”是此次问题的要求。附件会拼进用户消息并保存，不会自动入库。需要长期使用的规则要另建知识库。

### 对照二：空绑定子领域

新建 `LAB 空绑定对照` 子领域，正文只写“如实说明缺失资料与工具”，知识、Skill、MCP 都不勾选，确认已发布。新建对话选择它，要求读取计费手册核验码并查询当前状态。

期望没有知识来源、没有工具摘要、不能取得三类核验码或当前状态。它仍可能提供模型的一般运维知识，这不等于读取了工作空间资源。空绑定并非“无限制”。

### 对照三：参数越界

到“执行与审批”提交 `service_status`，目标环境保持 test，参数改为：

```json
{"service":"outside-scope","environment":"test"}
```

期望提示“工具参数 service 超出授权范围”，MCP 终端成功查询条数不增加。使用确定参数入口能直接验证平台策略；仅让模型回答“不能查”并不能证明后端拦截生效。

### 对照四：MCP 不可用

仅在教学环境中，对启动示例的终端按 Ctrl+C，然后新建对话要求查询当前状态。应明确未取得实时结果，不能拿旧会话的 1260 / 37 伪装成新结果。握手/发现失败会保存独立的“未取得实时数据”提示；若命中目录缓存后才在调用阶段失败，则查看实际工具失败摘要和执行记录。

2026-09-27 已修复发现失败只有短暂进度的问题：最终回答、待审批和已保存错误消息均保留服务名和固定说明，刷新后可回看；模型同时获知本轮证据缺失。发现阶段没有执行工具，因此不伪造工具步骤。回 MCP 详情重新“连接并发现工具”检查；恢复时重新运行本教程命令，连续连接失败可能触发约 30 秒熔断。

### 对照五：发布门禁和普通成员权限

只在练习资源上修改子领域职责并保存，暂不发布，再回到原会话发送问题。应提示“当前子领域未发布或已停用”；重新发布后可继续。编辑 Skill 后成为草稿时，该 Skill 会不再加载，不应把它与子领域草稿导致整轮拒绝混为一谈。

再用指定普通成员账号验证：先没有私有资源权限，再由管理员逐项授予读者权限和符合策略的工具使用资格。核对授权前后能看到什么、调用什么。不要为方便实验把所有资源改成公开；当前“公开”指所有已登录工作空间成员可读。

**本课验收：** 对正常、缺资料、缺工具、越界、未发布分别有可解释结果，并记录没有覆盖的情况。历史答案里已经交付的资料不会因为后来撤权自动消失。

## 第九课：把成功的排障变成巡检任务

进入“定时任务 → 创建定时任务”，名称 `LAB 计费巡检试跑`，处理 Agent 选择 `LAB 计费测试排障`。复制这段自包含指令：

```text
检查 billing-lab 的 test 环境。
调用获准的 service_status 查询当前状态，对照绑定手册的 P95 与连接池等待阈值。
按绑定 Skill 输出观察事实、阈值对照、排查建议、来源与缺口。
注明采样时间与窗口；fixture=true 必须写为教学模拟数据。
没有工具返回时明确未取得实时数据，不执行任何写操作。
```

选择 Cron `0 9 * * *`、时区 `Asia/Shanghai`，表示上海时区每天 09:00。安排在距离当前足够远的时间保存，随即暂停，再点“立即执行”试跑。任务记录约每 5 秒刷新；完成后点“查看会话”，应能看到独立会话、知识与工具证据。练习结束保持暂停。

每次任务新建会话，不能写“再查一遍刚才的服务”；服务、环境、工具、输出要求必须写完整。暂停只停止未来自动触发，不撤销当前执行；暂停任务仍能手动运行。手动运行不改变下次自动时间，单次任务试跑后也可能在原计划再执行一次。页面当前不提供任务编辑，修改指令或 Cron 需新建替代任务并处理旧任务。

原验收报告验证的是“暂停 + 手动试跑”，没有用网页证明生产定时到点触发。自己的环境需要单独安排近未来测试时间，保持应用在线，等待实际自动执行并保存记录。不要把手动成功当成定时运行完成。

任务结果默认保存在站内；若要企业微信、邮件或工单通知，需要配置通知 Webhook，并由接收系统转换和投递。普通自然语言聊天没有内置“创建定时任务”工具。

## 第十课：把教学数据源替换成自己的系统

### 先填一张接入需求卡

| 项目 | 需要填写的真实内容 | 例子仅说明格式 |
| --- | --- | --- |
| 第一个场景 | 一个范围清楚的只读问题 | 订单服务近 5 分钟超时排查 |
| 唯一目标 | 服务、环境、集群 / 命名空间 | order-api / staging / order-test |
| 实际数据源 | 监控、日志、发布或 CMDB 的接口 | 内部状态聚合 API |
| 工具参数 | 允许的目标与查询范围 | service、environment、windowMinutes |
| 返回字段 | 值、单位、窗口、采样时间和来源 | P95 毫秒、等待数、sampled_at |
| 业务依据 | 经负责人确认的阈值与处理手册 | 团队正式 SLO 和排障规范 |
| 使用者 | 谁能问、谁维护、谁发布 | 值班人员、系统负责人、管理员 |
| 接入凭据 | 远程只读身份及保管方式 | 受限监控服务账号 |
| 验收方式 | 如何与原系统核对 | 同目标、同统计窗口对比原监控页面 |

先选一个能核对结果的只读接口，不必一次接数据库、Kubernetes、工单、日志和全部服务器。

### 路线 A：你的系统已经提供 MCP

让系统负责人提供 **Streamable HTTP endpoint**、访问方式、工具名称和参数 schema。按第五课配置地址、Token、发现和允许列表；逐项配置工具策略，再绑定进子领域。

只提供 `stdio` 启动命令或旧 SSE 地址时，当前工作空间不能直接连接；需要服务方提供兼容 HTTP 入口或单独部署适配服务。网页 URL、Swagger 地址或普通 REST API URL 也不能直接当 MCP 地址填写。

### 路线 B：你的系统只有 REST API

需要增加一个小型 MCP 适配服务。工作空间调用 `service_status`，适配服务校验参数后请求你的只读 REST API，再把结果整理成 MCP 返回。应用本身不会自动转换 REST API。

练习的 `mcp-demo.mjs` 已包含协议入口、工具定义和返回结构；替换其中 `queryStatus()` 就是最小改造点。以下示例假设你们提供一个**约定好的状态聚合接口**，不是任意监控产品的原生接口：

```text
GET https://ops-api.example.com/api/service-status?service=billing-lab&environment=test
Authorization: Bearer <适配服务自己的只读令牌>
```

预期 JSON 合同如下；数值仅用于说明字段，实际必须来自上游查询：

```json
{
  "service": "billing-lab",
  "environment": "test",
  "status": "degraded",
  "p95_ms": 1260,
  "connection_pool_waiting": 37,
  "sampled_at": "2026-09-20T01:00:00Z",
  "window_minutes": 5,
  "source": "internal-monitoring"
}
```

可用下面函数替换示例的 `queryStatus()`。它使用脚本已经导入的 `z`，从适配服务进程环境读取固定 URL 和令牌，不接收模型传入的 URL；设置超时、禁止重定向、限制响应体、校验字段后仅返回约定内容。

```js
async function queryStatus({ service, environment }) {
  const endpoint = new URL(process.env.OPS_STATUS_URL);
  if (endpoint.protocol !== 'https:' || endpoint.username || endpoint.password) {
    throw new Error('需要固定的 HTTPS 状态接口');
  }
  const token = process.env.OPS_READ_TOKEN;
  if (!token) throw new Error('未配置只读接口令牌');
  endpoint.searchParams.set('service', service);
  endpoint.searchParams.set('environment', environment);
  const response = await fetch(endpoint, {
    method: 'GET',
    headers: { Authorization: `Bearer ${token}`, Accept: 'application/json' },
    redirect: 'error',
    signal: AbortSignal.timeout(8000),
  });
  if (!response.ok) {
    await response.body?.cancel();
    throw new Error(`上游状态码 ${response.status}`);
  }
  const reader = response.body?.getReader();
  if (!reader) throw new Error('上游未返回正文');
  const chunks = [];
  let bytes = 0;
  try {
    while (true) {
      const { value, done } = await reader.read();
      if (done) break;
      bytes += value.byteLength;
      if (bytes > 64000) {
        await reader.cancel();
        throw new Error('上游结果超过 64 KB');
      }
      chunks.push(Buffer.from(value));
    }
  } finally {
    reader.releaseLock();
  }
  const data = z.object({
    service: z.literal(service),
    environment: z.literal(environment),
    status: z.enum(['healthy', 'degraded', 'down', 'unknown']),
    p95_ms: z.number().finite().nonnegative(),
    connection_pool_waiting: z.number().int().nonnegative(),
    sampled_at: z.string().datetime({ offset: true }),
    window_minutes: z.number().positive(),
    source: z.string().min(1).max(200),
  }).parse(JSON.parse(Buffer.concat(chunks).toString('utf8')));
  return { ...data, fixture: false };
}
```

配置 `OPS_STATUS_URL` 为固定真实接口，`OPS_READ_TOKEN` 通过适配服务的 Secret / 环境注入提供。仅在上游已确认为真实监控时使用 `fixture:false`；如果连的是沙盒或模拟平台，继续标识模拟来源。不要把调用时间伪装成监控采样时间；陈旧数据、空查询结果和未知状态应按接口合同明确返回或报错。

这个函数是接入模板，未连接你公司的接口。它仍保留演示脚本中的 `billing-lab/test` 范围检查；改成自己的目标时，按下一节同步全部配置。上游字段、认证、分页和错误结构不同时，要在这里做明确映射。例如 P95 原单位是秒时转换为毫秒，不能原样填入 `p95_ms`。GET 方法和 `readOnlyHint` 都不证明业务实现只读，需要接口负责人确认它没有副作用。

如需单独部署此适配服务，将它作为独立项目，保留必要依赖并锁定版本；教程直接使用本仓库已经安装的 SDK、Express 和 Zod。对外提供真实 MCP 前，还需实现入口鉴权、部署网络限制、日志脱敏、监控和服务生命周期管理。本机无鉴权教学脚本只适用于本机练习。

### 分清三组凭据和两条网络链路

| 凭据 / 链路 | 保存或检查的位置 |
| --- | --- |
| 模型 API Key | 工作空间“模型服务”配置，后端用于访问模型 |
| 工作空间访问 MCP 的 Token | MCP 资源的 Bearer Token；由 MCP 服务验证 |
| MCP 访问业务 API 的只读令牌 | 适配服务自己的 Secret，例如 `OPS_READ_TOKEN` |
| 工作空间后端 → MCP | 后端网络可达、TLS、Token、应用出口允许列表 |
| MCP → 监控 / 日志 / 业务 API | 适配服务网络、上游认证和业务权限 |

工作空间的 MCP Token 不会自动变成业务 API Token；模型不需要知道这些令牌。独立 MCP 服务的出口也不受工作空间 `OUTBOUND_*` 自动保护，需要单独配置。

生产部署时，工作空间至少配置允许访问的精确 origin；origin 是“协议 + 域名 + 端口”，不包含 `/mcp` 路径。例如把真实 MCP origin 加入 `OUTBOUND_ALLOWED_ORIGINS`，若解析为内网地址还需 `OUTBOUND_PRIVATE_ORIGINS`。明文 HTTP 另需显式允许。不要以通配开放或关闭 TLS 校验排查连接问题，完整启动要求见[生产治理](production.md)。

### 从教学替换成真实目标时，逐项核对

| 位置 | 必须替换 / 核对的内容 |
| --- | --- |
| 知识正文 | 真实服务、环境、单位、窗口、阈值、维护人与版本；去掉教学核验码 |
| Skill | 实际工具名、必要参数、故障流程；去掉练习核验码，保留数据缺失处理 |
| MCP 实现 | 参数 schema、服务端目标允许列表、真实 API、结果映射和错误处理 |
| MCP 表单 | endpoint、Token、服务标识与目标环境 |
| 工具授权 | 真实工具名、roles / userIds、environments、constraints |
| 子领域 | 职责、绑定到真实资源、使用者权限、发布状态 |
| 任务 | 自包含的真实目标、Agent、时间、时区；先暂停试跑 |
| 验收 | 与原系统同一目标、同一窗口对比，不再以固定教学值为通过条件 |

不要只改名称或把 test 改成 production 就认为接入完成。先在你自己的测试 / 预发布系统跑通只读链路，再由系统负责人确认生产只读范围。

### 已实现案例：本机接入 DTS cn_east 任务状态

本仓库已提供独立的 [DTS MCP 适配器及完整部署说明](../integrations/dts-mcp/README.md)。它把 DTS 的 `GET /proxy/v1/jobns/getstatus` 包装为 `dts_get_job_status`，运维助手连接本机 `http://127.0.0.1:43129/mcp`。DTS 后端和运维助手核心执行链路保持原有实现。

这次接入限定 `business_domain=general`、`area_name=cn_east`。初次使用单任务允许列表，用户确认拥有该区域全部任务查看权后，当前本机已设置 `DTS_JOB_SCOPE=region`，支持该范围内任意有效任务 ID。本机通过 launchd 保持适配器运行；四个私有资源分别为 `DTS cn_east 状态说明`、`DTS cn_east 只读查询`、`DTS cn_east MCP`、`DTS cn_east 运维`。已审阅的 Skill 与子领域已发布，只有指定管理员能使用这个工具。

在前台新建对话，Agent 选择 **DTS cn_east 运维**，开启知识检索，输入：

```text
查询 DTS 任务 12345678901234567 的当前状态，业务域 general，区域 cn_east。
报告 health、paused、manual_stopped、finished、worker 延迟、上报时间和数据新鲜度。
仅做查询，时间注明北京时间。
```

接入时的三个关键区别：任务 ID 全程为字符串；DTS `data.status` 还需二次 JSON 解析；DTS 的 `operator` 和工号不代表鉴权。适配器用独立 Token、固定目标和明确的任务范围模式控制访问，不让模型传入 URL 或操作者身份。

工具返回真实上报时间、查询时间与 freshness。超过默认 60 秒标记过期，缺失值保留 null，查询失败明确报错，不把查询时间冒充上报时间。只输出有限状态字段，不将原始 inbound/outbound/config 送入模型。paused、finished 和 worker 延迟的含义见绑定知识，不据单一字段推断根因。

本机运维命令（仓库根目录）：

```sh
npm run dts:local -- status
npm run dts:local -- restart
npm run dts:local -- stop
# stop 后重新加载已有本地配置
npm run dts:local -- install
```

首次安装、Token 保存方式和切换范围见适配器说明；源码中仅包含占位配置，本机真实地址和随机 Token 存在 Git 忽略的 `.env.dts-mcp`（0600）。区域模式需清空 `DTS_ALLOWED_JOB_IDS`，执行 `npm run dts:local -- sync-policy --owner admin` 移除工具策略的 `constraints.jobid`，再重启适配器。保留 `business_domain=["general"]` 与 `area_name=["cn_east"]`；不能把 jobid 设置为 `*`。仍需传入具体 jobid，不会批量枚举任务。

`provision --owner admin` 是显式本机管理员初始化命令，复用应用加密、版本、知识索引与审计函数，创建四项已审阅资源；不会创建登录会话或修改模型配置。`sync-policy` 只同步现有 DTS 工具的任务 ID 约束并保留其他权限。网页验收使用已有登录账号，覆盖发现、对话、知识引用及执行记录。

本次真实联调结果与独立模拟测试分开记录于 [验收与验证记录](verification.md)。Mac 睡眠、关机或退出登录期间本机服务不可用；不代表远程生产高可用部署，也没有开通 DTS 写操作或其他区域。

## 第十一课：多个系统、多个团队怎样组织

以订单和数据库运维为例，可以这样分配：

| 子领域 | 知识库 | Skill | MCP 工具范围 |
| --- | --- | --- | --- |
| 订单测试排障 | 订单测试阈值、依赖与发布手册 | 通用只读排障 + 订单检查步骤 | 测试监控、脱敏日志，只允许订单测试目标 |
| 订单生产巡检 | 生产 SLO、值班与升级规则 | 巡检报告格式 | 生产只读状态，限制目标、时间窗口和返回量 |
| 数据库容量分析 | 容量标准、增长处理手册 | 容量分析流程 | 容量 / 慢查询统计，不开放任意 SQL |

可以复用同一个通用 Skill，但应避免多个 Skill 写互相冲突的输出格式或步骤。不同环境的阈值分别维护，子领域明确绑定。每类资源可以绑定多个条目，但并不表示全部知识正文都会进入上下文，也不表示绑定 MCP 中的每个工具都被授权。

子领域绑定的粒度是整个 MCP 资源，不能在子领域表单里再为该 MCP 单独挑工具。如果两个领域需要同一 endpoint 的不同工具子集，可以建立两个 MCP 资源，分别维护允许列表、工具策略与读者权限，再各自绑定。

这属于工作范围配置，**不是全局禁止一个用户在别处使用更多资源的安全边界**。同一用户在通用 Agent 或执行中心的能力仍取决于其资源 ACL 和工具策略。要做到订单值班人员不能访问数据库管理能力，就不要授予相关资源读者权限或工具执行资格；当前没有独立租户隔离。

维护顺序建议为：资料负责人维护知识 → 流程负责人修改 Skill → 管理员审核发布 → 运维人员在测试子领域复测 → 再开放给目标成员。当前没有双槽位发布，需要不影响现有用户时，创建独立候选资源与测试子领域，验证后再调整正式绑定并重新发布。

## 第十二课：何时用聊天、任务、Runbook 和审批

| 需求 | 使用入口 | 执行特点 |
| --- | --- | --- |
| 临时排障，步骤随证据变化 | 聊天 + 子领域 | 模型决定是否调用获准工具 |
| 定期出状态报告 | 定时任务 + 子领域 | 每次独立会话，仍由模型分析 |
| 确定工具与参数的单次操作 | 执行与审批 | 只读直接执行；写操作先审批 |
| 固定步骤、固定目标的标准操作 | 已审核 Runbook | 不让模型临时生成步骤参数 |
| 告警触发固定流程 | 签名 Runbook Webhook | 外部发送事件 ID，不能随告警注入工具参数 |

Skill 是处理指令，Runbook 是已审核的固定执行步骤，它们不能互相替代。当前最多八步的 Runbook 需要另一位管理员审核发布；自动低风险写还需相应策略与部署开关，高风险不进入自动流程。完整配置见[生产治理](production.md)。

从只读升级到重启、扩容等变更时，至少需要明确目标范围、远程幂等参数、只读结果核验和恢复说明。模型提出写调用后，系统保存待审批计划并结束本轮；批准后的步骤独立执行，不自动恢复原来的模型对话。生产或高风险操作需要另一位管理员批准。

“幂等”表示同一个操作标识重复到达远程端时不会重复产生副作用，必须由远程工具实现；仅添加 `idempotencyKey` 字段不算实现。写请求发出后结果不明时可能标为 `unknown`，应查询实际状态，不盲目重试。取消、暂停和紧急停止都不能撤销已发生的远程操作。

本课程的第一阶段到真实**只读运维**即完成接入目标；生产变更需针对真实工具再做专项验收，不能沿用教学服务结果。

## 第十三课：遇到问题按链路定位

| 现象 | 先检查什么 | 下一步 |
| --- | --- | --- |
| 页面能开，模型没回复 | 已保存配置、模型 ID、额度、网络 | 先做模型测试，再发简单问题 |
| 模型测试过了，却不调用工具 | 模型工具兼容性、发布 / 绑定、工具发现与策略 | 先用执行中心证明工具可用，再用明确查询问题测试模型 |
| 知识存在却没有来源 | 知识开关、启用、有效期、读者、绑定、查询关键词 | 用明确服务名和故障关键词新建对话 |
| 答案混入其他系统资料 | 是否在通用 Agent，绑定是否过多 | 使用专用子领域和少量明确资料 |
| Skill 列表已启用却没效果 | 详情是否“已发布”，是否绑定，有无冲突 Skill | 发布已保存版本，再开新对话 |
| ZIP 报入口错误 | SKILL.md 大小写、层级、数量、压缩大小 | 解压检查，重打单层技能目录 |
| ZIP 上传提示接口不存在 | 前端新、3001 后端旧 | 正常停止旧后端，重启当前代码；保留原数据目录 |
| 发现工具失败 | 是否是 MCP endpoint、协议、Token、后端网络 | 详情重新发现，检查 MCP 日志；不要只测浏览器可达 |
| 工具存在但拒绝执行 | 允许列表、策略、角色、用户、环境、参数范围 | 与真实 schema 一一对照，不把限制全部删除 |
| MCP 有返回但指标含义不对 | 秒 / 毫秒、统计窗口、目标、陈旧数据 | 和原系统同条件查询比对 |
| 原会话突然不能继续 | 子领域是否编辑后未发布或被停用 | 核对详情、审核后重新发布 |
| 工具断开或缺少实时数据 | 区分发现失败、实际调用失败和本轮未调用 | 看消息的数据源提示、实际步骤、发现结果及 MCP 端记录；升级前旧消息不会补写历史证据 |
| 任务手动成功但没自动执行 | 暂停状态、下次时间、时区、服务是否运行 | 单独验收到点触发，不能用手动记录代替 |
| 任务说不知道“刚才的服务” | 指令依赖历史 | 新建完整自包含任务 |
| 修改了资源但旧回答还在 | 会话保存了过去交付的内容 | 新建会话复测；撤权不删除历史回答 |

模型自述不是排错的唯一依据。优先查看资源详情、知识来源、执行步骤、会话管理、审计日志和 MCP 端记录。服务端日志与导出证据只保留必要业务字段，勿包含 Cookie、Token 或原始敏感日志。更多部署故障见[运维与接手](operations.md)。

## 第十四课：自己的系统接入后，怎样证明可交付

### 为每个场景保存一张验收表

复制下面表格，填写“实际结果 / 证据位置”，不要直接复制预期作为通过结论：

| 编号 | 验收内容 | 通过条件 | 实际结果 / 证据位置 |
| --- | --- | --- | --- |
| 01 | 模型与账号 | 指定用户能登录，模型测试和真实回复成功 | 待填写 |
| 02 | 知识依据 | 正确版本、正确阈值、来源属于指定系统 | 待填写 |
| 03 | Skill 发布 | 草稿不加载，发布后按审核流程输出 | 待填写 |
| 04 | MCP 确定调用 | 执行中心与 MCP 日志能对上服务、环境、参数 | 待填写 |
| 05 | 组合问答 | 正确引用资料，并实际调用工具 | 待填写 |
| 06 | 数据准确性 | 与原系统同目标、单位、窗口核对一致；记录采样差异 | 待填写 |
| 07 | 范围与身份 | 越界被拒绝，普通成员不能读 / 调未授权资源 | 待填写 |
| 08 | 失败处理 | 工具断连 / 上游失败时不编造实时结果，记录已知观测缺口 | 待填写 |
| 09 | 上下文与附件 | 新会话无跨会话记忆，附件不自动入库 | 待填写 |
| 10 | 调度 | 手动试跑、真实到点触发分别验证；生产任务时区正确 | 待填写 |
| 11 | 留存与恢复 | 刷新 / 重启仍能查看记录，在新目录实际恢复备份 | 待填写 |
| 12 | 通知与负责人 | 若启用通知，实际送达且重复事件能去重；明确值班人与处理方式 | 待填写 |

每条证据记录时间、使用者、模型 ID、资源 revision / 文档版本、会话或执行 ID、工具端对应记录。教学核验码帮助初学者理解来源；真实业务验收应依靠接口返回、版本和独立系统比对。

### 正式使用前的交接内容

- **资源清单：** 每个子领域绑定什么、谁可读、谁维护、谁发布；工具允许操作哪些目标。
- **运行位置：** 应用、MCP、业务 API 各部署在哪里；谁维护网络、证书和凭据。
- **数据维护：** 手册来源、更新周期和失效处理；日志与指标的采样窗口、保留时间和脱敏规则。
- **故障处理：** 模型或 MCP 不可用时如何人工查询；通知发给谁；未知写结果如何核对。
- **备份恢复：** 数据目录、主密钥与独立备份密钥保管方式，实际恢复记录及恢复耗时。
- **容量边界：** 当前单实例 SQLite、模型和工具配额、并发 / 预算配置；不按多副本高可用交付。

生产必需的 HTTPS、Cookie、身份模式、外置主密钥、网络出口和备份命令请按[生产治理](production.md)执行。本项目未提供向量检索、PDF/OCR、自动领域路由、多 Agent 委派或脚本沙箱。把这些列为明确的后续需求，不要假设上传一个技能包就会获得它们。
