# 写入结果未知实验：先确认事实，再决定下一步

本实验对应[学习路线](agent-learning.md)第4单元。一次写请求已经发出，响应却丢失时，平台既不能宣布失败，也不能直接再写一次。`unknown` 保存这种不确定性；取消本地等待也无法回滚远端副作用。

四组实验使用本机MCP、临时SQLite及合成内存状态。通过固定工具计划、审批、取消和只读核验接口走真实持久执行器，运行标签为 **direct / 1**，模型调用与tokens为0。它不使用模型生成计划，也不是AgentScope编排实验；复用测试初始化设施不代表调用了SDK。

## 运行与报告

在仓库根目录安装项目依赖并使用Node ≥22.16后运行：

```sh
npm run agent:learn:unknown
```

报告写入 `test-results/learning/unknown-lab.md` 和 `unknown-lab.json`，包含每个检查点的run/step状态、HTTP、写请求/应用次数、只读核验、槽位和源码摘要。重新运行会覆盖报告，比较前先保留副本。实测结果见[验证记录](verification.md)，下表是预期。

脚本不接受参数或真实模式，不加载 `.env`、业务数据库或真实供应商配置。每组使用独立临时数据，资源环境固定test，只允许合成billing目标写为maintenance及对应只读核验；写操作仅改变fixture内存。费用配置固定为0，调度关闭，不连接真实通知渠道。

## 四组对照

每组先创建固定计划，观察 `202 / awaiting_approval` 且写请求数为0，再触发故障。

| 场景 | 受控故障 | 收尾后run / step | 代理收到的写请求 / fixture应用次数 |
| --- | --- | --- | --- |
| 发送前失败 | 计划创建后改变资源修订，再审批 | failed / failed，409 | 0 / 0 |
| 写后丢失回包 | 上游已应用写并返回，代理丢弃回包 | unknown / unknown | 1 / 1 |
| 发送前取消 | 工具目录发现停在屏障中，接受取消后收尾 | cancelled / cancelled，审批409 | 0 / 0 |
| 写后取消 | 上游已应用写，代理暂扣回包，接受取消后收尾 | unknown / unknown，审批409 | 1 / 1 |

第二组随后调用只读核验，目标状态匹配后run/step转为success；只读请求增加，写请求和实际应用次数仍各为1。重复批准应409，不能产生新写请求。传输故障的审批HTTP映射以报告实测为准，不能凭“回包丢失”猜测其错误码。

取消接口的即时200表示接受取消，必须等待原审批调用退出后再回读最终状态。特别是写后取消，最终可能从即时cancelled收敛为unknown；不能截取中间状态宣称“远端没有执行”。

## 两种计数与两种观察视角

**写请求数**在本地代理收到 `tools/call` 写请求时增加；**应用次数**在fixture按幂等键真正改变合成状态时增加。fixture会按键去重，因此“应用一次”不足以证明平台没有重发。实验同时核对两者，并在重复审批和对账后检查它们不增加。

测试观察器能看见代理已经收到上游回包和fixture实际应用的事实；业务平台只知道写请求已发出，未拿到可信完成结果，所以保存unknown。本次合成故障中确实已经写入，但不能将unknown普遍解释为“肯定写成功了”。其他网络故障也可能根本未到达目标。

只读核验确认的是配置的状态条件当前成立，不是恢复原始回包，也不能普遍证明这个状态仅由本次写入造成。它不重新运行模型、不重新执行写请求，也不自动恢复尚未执行的后续Runbook步骤。

## 源码与检查点

| 位置 | 负责的事实 |
| --- | --- |
| [实验脚本](../scripts/learn-agent-unknown.mjs) | 有限等待的目录/回包屏障，实际丢弃响应，以及检查点报告 |
| [固定执行器](../server/execution.mjs) | callStep保存计划；approve执行固定步骤；executeStep区分发送前失败与发送后unknown；cancel中止等待；reconcile只读对账 |
| [本地fixture](../tests/fixtures.mjs) | billing合成状态、幂等去重与实际应用记录，绝不连接生产服务 |
| [执行回归](../tests/execution.test.mjs) | 审批、取消、恢复、unknown和不重放边界 |

`executeStep` 的 `sent` 是平台开始调用工具的边界，单靠它不能证明远端收到请求。实验代理提供额外观测，不能把测试观察能力归给实际生产平台。

资源停用或身份撤销的在途核验复查由[执行回归](../tests/execution.test.mjs)单独覆盖：工具发现后及读取结果后均重查，变化时保留unknown。这个四组教学实验不模拟该并发场景，也不据此宣称所有撤权边界均已验收。正常结束及初始化成功后的捕获异常会释放屏障并关闭本轮临时资源；初始化中断或强制退出不保证清理，未做信号中断验收。

## 写一份故障复盘

先运行实验，再用自己的报告完成下表，不把这里的预期当成个人实测：

| 问题 | 应引用的证据 |
| --- | --- |
| 平台确实发出了什么？ | 代理的write请求数与计划ID |
| 测试观察器知道远端发生了什么？ | fixture应用次数、回包已被代理收到的检查点 |
| 平台为何只能记录unknown？ | 审批错误、run/step、原始回包没有交付 |
| 取消后为什么不能宣布已回滚？ | 写后取消的最终unknown与应用次数1 |
| 为什么不直接重新审批？ | 重复审批409且write请求不增加 |
| 只读对账确认了什么？ | 只读请求增加、verification匹配、状态转success、写数不变 |

三分钟讲解可以这样组织：“我用真实固定执行器和本地代理制造了发送前失败、写后回包丢失和取消两种时点。发送前没有写请求；发送后平台无法确认结果，必须保留unknown。我分别计数请求与实际应用，证明只读对账没有重发写入。这是本地治理和故障处理证据，不能推出跨网络exactly-once，也不能把取消理解成事务回滚。”

继续思考：如果核验时状态恰好被另一位操作者改变，还需要什么业务操作ID、版本或事件证据？如果读取也失败，应保留怎样的不确定性？这些需要真实业务契约，不由本地成功样例替代。
