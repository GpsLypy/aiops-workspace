# 可观测性实验：慢在哪，失败在哪，完成意味着什么

本实验对应[学习路线](agent-learning.md)的观测主题，用实际脱敏全景、持久执行台账和本地观察器解释一轮Agent。全景记录可观测节点与依赖，不是模型私有思考链，也不会替你判断业务健康。

## 运行

需要Node ≥22.16、Python 3.12、已锁定AgentScope 2.0.8与项目依赖：

```sh
npm run agent:learn:trace
```

脚本只用本机模型、只读MCP和每组独立临时SQLite，不读取正常`.data`/`.env`或真实供应商凭据，不接受参数/真实模式。固定prefork、test环境、service_status/billing授权、零费用单价与零日费用限额。模型决策与成功响应的30tokens均预设，不发生真实模型费用或生产调用。

输出为 `test-results/learning/trace-lab.json` 与 `.md`，再次运行会覆盖，请先保存要比较的报告。JSON的`results[].actual.trace`是实际持久快照；`fixtureObservation`是本地观察器记录，两个来源不能混用。报告含时间、22文件源码摘要、清理结果和明确未验证边界。本次实际结果见[验证记录](verification.md)。

## 四组预期

| 场景 | 操作 | 应观察的事实 |
| --- | --- | --- |
| 模型等待 | 第一次模型响应前注入160ms等待 | 模型节点耗时覆盖实际等待，仍完成2次模型请求和1次工具 |
| 工具等待 | 只读工具返回前注入160ms等待 | 工具节点耗时覆盖实际等待，流程与上组计数相同 |
| 工具错误 | MCP返回isError=true | HTTP502、run/step failed、trace error；模型1次/30固定tokens，实际工具1次 |
| 查询完成但业务异常 | 成功返回合成degraded与约两分钟前的reportedAt | HTTP200、run/step success、trace completed；模型2次/60固定tokens，不能称业务健康 |

前三组与第四组都实际经过SDK和HTTP/MCP协议。失败组相同幂等键重放返回409，让用户核对原执行；成功组回读200。两种情况都不重跑模型或工具。实验不是自动重试策略。

## 时间的三种口径

`fixtureObservation.injectedWait`给出测试端等待的起止和实际毫秒；`delayedNodeMs`来自相应真实节点，除了等待还包含本地协议等工作。只核对节点覆盖等待的下界，不要求它一定是全轮最慢阶段，也不拿两个样本比较模型供应商性能。

`trace.startedAt/finishedAt`与节点时间记录处理过程，来源是服务端时钟。节点有包含和先后关系，直接相加可能重复计算；这里没有跨请求P95、排队时间或外部OpenTelemetry链路。

`fixtureObservation.reportedAt`是合成工具数据声明的快照时间，脚本另与持久工具返回、第二次模型输入核对。它不在全景里：全景刻意不保存工具正文。图谱结束时间较新，不能证明业务数据较新；实际新鲜度还需业务规则和可信数据源。第四组没有执行巡检判定器，只说明当前图谱不自动判定业务健康或新鲜度。

## 失败与成本怎样解释

工具失败并不意味着没有付出模型用量：模型已先提出工具请求，执行台账记录30固定tokens，而工具步骤随后失败。正常两次模型请求记录60。脚本交叉核对实际请求数、模型节点用量和run.tokens。

这些固定数字只验证记账口径。`realCost=null`表示没有真实账单；不能写成“费用为零”或拿固定tokens推算优化比例。平台的零单价仅隔离教学配置，不说明真实服务如何收费。

工具错误节点能指出失败发生在工具阶段，runId可关联执行中心步骤；当前错误节点未必带步骤ID，不能补造关联字段。报告里的steps来自按runId查询的真实台账，本实验每轮恰好一个工具步骤。

## 源码路线与练习

| 源码 | 要解释的责任 |
| --- | --- |
| [实验脚本](../scripts/learn-agent-trace.mjs) | 本地等待/错误/状态输入、观察器、断言与报告 |
| [全景采集](../server/agent-trace.mjs) | 有界节点/边、脱敏、时间、终态与快照 |
| [模型运行时](../server/agent-runtime/index.mjs) | 实际请求开始/结束、固定usage入账和请求模型身份 |
| [Agent](../server/agent.mjs) | 工具/答复节点、错误收尾与消息持久化 |
| [执行器](../server/execution.mjs) | run/step状态、费用口径与幂等键回读 |

先运行实验，记录两种等待对应的节点ID和实际毫秒；再找到工具失败的run/step，解释为何仍有模型tokens。最后解释第四组的三个事实：查询调用成功、合成业务异常、图谱未记录业务快照时间。不要把“未记录”写成“没有问题”。

面试表达可用：“我在［本人实际执行时间和报告］用本机故障注入核对了模型等待、工具等待和工具失败。图谱能定位处理阶段，台账能确认步骤与用量，但执行成功并不代表业务健康。快照时间要从业务证据检查，费用要另对账，不能从图谱或fixture补造。”

当前仅本机受控样本，未做真实供应商性能、生产监控、人工质量评价、跨浏览器或强制终止清理验收。正常收尾会关闭本轮临时应用、Worker和MCP；初始化中断或强制退出不保证清理。用户亲自复现与贡献记录仍需自己填写。
