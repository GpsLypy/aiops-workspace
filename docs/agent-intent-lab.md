# 授权与意图实验：有权查询，也可能查错对象

本实验对应[学习路线](agent-learning.md)第3单元。用户明确要求查询 billing，管理员允许查询 billing 和 inventory。如果模型改查 inventory，参数结构、权限和工具执行都可能成功，但这次请求没有被正确满足。实验把这一缺口与真正越权的 payroll 对照，帮助解释权限治理的责任边界。

2026-10-04 的原实验使用当时的 Node 实现、真实 AgentScope 2.0.8 / prefork、临时 SQLite 和本机受控模型/MCP。目标全部是合成标签，工具只读，模型选择预设。实验资源未配置后续新增的 `requiredTargetFields`，所以重复运行仍用于展示未启用目标绑定时的风险，不是对新门禁的回归测试。

## 运行与报告

在仓库根目录完成[SDK安装](agentscope-runtime.md)后运行：

```sh
npm run agent:check
npm run agent:learn:intent
```

本次报告写到 `test-results/learning/intent-lab.md` 与 `intent-lab.json`，重复运行会覆盖这两个文件，比较前请先保留副本。报告包含预期/实际、五处目标证据、调用数、状态、时间与固定源码清单摘要。交付实测见[验证记录](verification.md)，下面的表是运行前的预期。

脚本只接受无参数本地模式，不加载 `.env`、正常业务数据库或供应商配置。每场景独立数据库，固定环境为test，仅授权 `service_status`；费用单价和每日费用限额固定为0，固定tokens只用于核对台账。正常结束及初始化成功后的捕获异常会清理临时服务、数据库和Worker；初始化中断、强制退出不保证清理，未做信号中断验收。

## 先写预期

三组保持同一明确查询 billing 的问题、同一 Schema、同一权限；唯一变化是受控模型提议的 `service`。

| 模型目标 | Schema合法 | 静态授权 | 预期实际工具调用 | HTTP / run | 模型次数 / 固定tokens | 满足本次目标 |
| --- | --- | --- | --- | --- | --- | --- |
| billing | 是 | 是 | 1次 billing | 200 / success | 2 / 60 | 是 |
| inventory | 是 | 是 | 1次 inventory | 200 / success | 2 / 60 | 否，已查错对象 |
| payroll | 是 | 否 | 0次 | 403 / failed | 1 / 30 | 否，调用被拒绝 |

三种参数都是合法字符串，所以第三组拒绝来自静态 `constraints.service`，不能把它解释成 Schema 发现了语义错误。目录发现只拿工具定义，不计作实际工具调用。

`scenarioMatched` 表示实际行为符合这一行的实验预期；`intentMatched` 表示模型提议的合成目标与预设用户目标相等，是执行后的脚本比较。第二组两者分别为true和false：实验成功复现了缺口，产品没有阻止这次错误查询。`run=success` 也只表示执行流程成功。

## 沿五处证据走一遍

1. **用户要求。** 同一个当前问题原样进入第一次模型请求，脚本预设目标为 billing；脚本没有自然语言目标解析器。
2. **模型提议。** 第一次受控响应提出 `mcp_0` 与 service 参数。模型可见目录只有一个允许的只读工具；别名不包含额外权限。
3. **实际调用。** 本机 MCP 的 `toolCalls` 记录收到的工具名和 service，而不是根据模型自述推断查询发生。
4. **持久步骤。** 在本场景临时数据库中读取并解密步骤参数，核对 service 和 success 状态。报告只保存合成目标等结构化证据，不导出密文、凭据或完整返回正文。
5. **工具反馈。** 第二次模型请求中的 tool 消息包含实际查询目标。先确认查了谁，再谈模型能否正确解释结果；不能靠最后一句“已确认”证明对象正确。

越权组应没有后面三处执行证据：无MCP调用、无持久步骤、无第二次模型请求。这是前置范围校验的有效证据。

## 实验时的前置绑定规范

以下是实验提出的下一步设计条件；其中单工具、单对象的结构化绑定已于 2026-10-08 实现，真实业务接入仍需单独验收：

- 从可信的本轮结构化选择或用户确认建立目标，限定资源、工具、规范化目标和轮次；不能把待校验的模型参数当成绑定来源。
- 缺失、含糊、多对象或上下文裁剪导致目标不可用时先澄清，不静默换用另一个已授权对象。
- 每次实际工具调用前，同时检查静态授权与本轮绑定。A允许且绑定A才能放行；B虽允许但不匹配应在发送前拒绝，实际调用数必须为0。
- 目标修改或新轮次需要明确的更新规则；后端重查身份和资源，绑定不能绕过既有撤权、Schema、审批与幂等机制。
- 分别验收正确A、授权内错误B、越权C、缺失/含糊目标、资源变化、多次调用与绑定过期。对自然语言解析另建代表性样本和人工复核，不能用本实验的精确字符串比较宣称识别准确率。

这个实验足以证明值得设计前置绑定，不能直接决定某个真实运维系统应使用哪些业务标识或信任来源；正式接入需要按该系统的交接和权限契约另行设计。

当前实现由用户在聊天或任务配置中明确确认目标，`targetBinding` 固定资源、工具、环境及策略声明的全部参数字段。声明 `requiredTargetFields` 的只读工具在调用前做精确比对，授权内换成其他对象、增加参数或从工具反馈改目标都会被拒绝；受控回归见 [目标绑定变更](../openspec/changes/agentscope-target-binding-20261008/proposal.md) 与 [验证记录](verification.md)。原实验的未配置工具仍会保留历史对照行为。自由文本不自动解析目标，单轮暂不支持多个工具/对象；DTS 真实资源必须先同步策略再验收，不能用本地合成通过代替生产结论。

## 三分钟面试讲解

“我把参数合法、授权允许、符合本次目标分成三个问题。工具Schema接收字符串service，管理员允许两个服务。用户要求billing时，受控模型改选inventory，真实SDK仍会完成一次查询并持久保存成功步骤；这证明授权范围并不验证当前意图。换成payroll则403，实际工具和步骤都是0，说明范围门禁工作正常。

我对照了模型参数、实际MCP调用、数据库步骤和下一次模型的工具结果，没有只看最终回答。这个实验使用固定模型决策，证明当时的治理边界，不能评价真实模型选错概率。建议下一步从可信本轮选择建立目标绑定，在调用前同时检查授权与意图；事后复核只能控制答复发布，不能撤回已经发生的查询。”

以上讲解保留实验完成时的表述。当前结构化目标绑定的实现范围见本章“后续设计与当前实现”；未声明目标字段的工具仍按原授权策略执行。

亲自运行后记录报告时间、源码摘要、三组实际数字和一个不符合直觉的观察，再按[面试材料](agent-interview.md)区分自己亲自复现、阅读理解与设计实现的贡献。
