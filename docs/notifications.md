# 巡检通知与企业微信

通知中心与定时任务位于同级菜单。第一期支持企业微信群机器人和通用 Webhook，支持按任务选择多个渠道、每次发送或异常时发送、持续异常提醒、恢复通知、失败重试和手动重发。执行状态、巡检结论、投递状态分别记录。

## 从创建渠道到第一次送达

1. 管理员打开“通知中心 → 创建通知渠道”，选择“企业微信群机器人”或“通用 Webhook”。
2. 填写渠道名称和接收地址。企业微信使用群机器人的 Webhook 地址；通用接收端可配置 Bearer Token 和至少 32 字符的签名密钥。
3. 指定允许使用的成员。默认仅管理员可用；成员只能将自己的任务发送至已授权渠道。群组接收者是外部读者，授权前确认信息范围。
4. 保存后点击“发送测试消息”。页面先显示已入队，再显示接收端确认的结果；企业微信必须返回 `errcode: 0` 才记为已送达。
5. 打开“定时任务 → 创建定时任务”，或已有任务的“通知设置”，勾选渠道。任务可以同时发送至多个渠道，各渠道结果独立。
6. 日报选择“每次执行结束”；周期检查可配置正常条件后选择“异常或无法判断时”，设置持续异常提醒间隔和恢复开关。
7. 查看格式预览并保存。点击“立即执行”，在执行记录中查看工具证据、业务结论和投递状态；点击“查看推送详情”可继续追踪。

地址和凭据加密保存，不回显完整地址。编辑时留空保留原值，通用渠道可勾选清除凭据。切换成企业微信会清除通用渠道的签名和 Bearer 凭据。渠道配置每次保存都会更新版本，尚未发出的旧版本消息会停止并给出原因；核对新配置后可以重发。停用渠道保留历史记录。配置与权限变更不能撤回已在途或已经被接收的消息。

正式环境需在 `OUTBOUND_ALLOWED_ORIGINS` 放行接收地址的精确 origin，内网需额外放行 `OUTBOUND_PRIVATE_ORIGINS`，明文 HTTP 需 `OUTBOUND_HTTP_ORIGINS`。使用现有固定 DNS 出口客户端，不跟随重定向。机器人 URL 中的 key 也是凭据，不应复制到任务指令中。

## 什么情况下算正常

| 维度 | 含义 | 状态示例 |
| --- | --- | --- |
| 执行 | Agent 是否完成了这轮执行 | 成功、失败、中断、等待审批 |
| 巡检 | 实际工具证据是否满足正常条件 | 正常、异常、无法判断 |
| 投递 | 接收端是否确认收到消息 | 待发送/重试中、发送中、已送达、发送失败 |

“执行成功”不能证明业务健康。正常条件只读取本次执行台账中只读工具的实际结果，不从模型回答提取健康标签。模型仍按现有指令决定调用工具；条件未触发所需工具调用时为无法判断。条件不会主动补发查询，也不自动发现巡检对象。

需要查询目标绑定的只读工具在任务创建时由操作人选择服务、工具、环境和策略指定的目标字段，并显式确认。该结构化目标随任务保存，调度每轮使用当前任务所有者身份重新核对资源、工具策略和绑定；模型尝试换成另一个授权目标时，实际调用前拒绝。旧任务迁移后的目标为空，页面显示“未确认目标”；如果尝试调用受保护工具，任务失败且不向 MCP 发出请求。使用“查询目标”逐条补录，不能从任务指令或巡检条件反推。普通未要求目标绑定的工具仍按原策略执行。

每条条件指定名称、MCP 服务、只读工具、结果字段路径、比较方式与期望值。字段可用点号访问嵌套对象。可在“限定检查对象”填写顶层参数的精确匹配条件；空对象匹配该工具本轮所有调用，无法证明未枚举对象也被检查。存在多个匹配调用时，全部结果都参与判断。

对象参数允许逐步编辑JSON；格式尚未完成时会阻止保存，修正后恢复。删除一条条件不会把它的输入或格式错误移给其他条件。切换“数据服务”会把该条件的对象参数重置为 `{}` 并清除旧格式错误，请按新服务重新填写；界面显示值与保存内容一致。

关闭已有任务的通知设置或未保存的新建草稿后，再创建任务会立即使用空条件、未选择渠道的通知草稿。勾选渠道后默认每次执行结束推送、持续异常提醒间隔60分钟、恢复正常时通知；不会继承上一次弹窗里的通知设置。关闭未保存的草稿不修改原任务。

- 等于/不等于按类型严格比较，数字 `1` 与文本 `"1"` 不相等且显示类型不一致。
- 大小比较只接受数字，不隐式转换字符串。
- 新鲜度填写允许的数据年龄秒数，时间字段必须为带时区 ISO 字符串；允许最多 30 秒未来偏差。过期、格式无效或更大的未来偏差均为无法判断。
- 缺少匹配调用、工具失败、字段缺失、脱敏值、类型不符或执行未完成均为无法判断。
- 任何条件缺少有效证据时，总结论为无法判断，同时保留已经发现的异常项；否则任一条件不满足为异常，全部满足才正常。
- 未配置条件的普通报告显示“未配置巡检判定条件”，可按每次执行结束推送；不能选择异常模式。

DTS 当前可按明确任务 ID 检查。例如先在任务“查询目标”确认 `jobid`、`business_domain`、`area_name`，再为 `dts_get_job_status` 配置对象参数 `{"jobid":"12345678901234567"}`，要求 `state` 等于文本 `running`，并增加 `reported_at` 新鲜度条件。巡检条件只匹配实际证据，不能代替前置目标确认。时间阈值应按业务约定配置，数据过期不代表已经证实业务故障。大 ID 必须为字符串；当前没有区域任务枚举能力。此处是配置示例，不代表已创建或验收真实定时巡检。

## 推送、抑制与恢复

每次执行结束都会保存事件快照；仅满足通知条件才创建投递。执行结果、结构化结论和事件/投递在同一 SQLite 事务内保存。重复处理同一 task_run 不会创建第二份事件。

每次模式发送所有结果。异常模式发送异常、无法判断和未完成执行；相同检查项状态在提醒间隔内抑制，检查项状态变化立即发送。恢复开关启用时，从异常/未知/执行未完成变为正常发送一次恢复消息。当前按每个任务/渠道跟踪状态，抑制从消息入队时计算，不等待对端成功。阈值内数值变化不自动视为升级；当前没有严重级别规则。编辑通知设置会重置抑制状态。

运行中不能修改通知设置。暂停任务只停止后续调度，不取消在途执行和已排队消息。删除任务会删除任务及运行记录，但会话、执行证据和通知快照保留；已入队消息继续投递，旧任务详情链接会提示任务不存在。渠道停用、用户停用或使用权限撤销会停止待发送消息。

发送使用持久队列，后台每 5 秒取最多 10 条、每批最多两条并发，每次网络请求超时 5 秒。网络故障、HTTP 408/429/5xx 自动重试；首次失败后等待至少 5 秒，随后指数退避，最多 8 次尝试，Retry-After 限制在一小时内。其他 HTTP 错误、重定向、出口拒绝、无效业务确认及企业微信永久错误直接失败。企业微信 45009 按限流重试。

“重新发送”只对失败记录有效，沿用原消息及投递幂等键，使用当前确认后的渠道配置；本轮尝试数归零，审计保留重发前次数。它不会再次运行巡检。渠道配置改变后自动重试也不会悄悄切换接收地址。

单实例进程启动将旧 running 任务标中断并生成对应事件，不重放工具；运行中租约过期也会补记中断。pending/sending 投递重启后继续处理。若对端已收到但本地未记录成功，可能重复发送，因此是至少一次投递。企业微信群机器人没有本系统的幂等去重保障，也没有群成员已读确认。

## 消息内容与协议

通用消息携带版本、事件 ID、事件类型、任务/运行/执行/会话 ID、执行状态、巡检结论与证据、完成时间、最多 2,000 字符的脱敏摘要。企业微信使用文本消息，UTF-8 限长 2,048 字节，超长内容截断；结论和检查项优先，配置详情链接时尽量保留链接。时间按任务时区显示，测试消息默认北京时间。

设置 `APP_ORIGIN` 后生成 `/#tasks?task=...&run=...` 详情链接。部署地址需要接收者可以访问；打开详情仍需登录及权限。未配置时不猜测 localhost 公网地址。群里的消息本身已经外发，站内权限不能撤回外部副本。当前使用现有凭据模式脱敏，不提供任意业务敏感数据分类器。

通用 Webhook 请求示意：

```json
{
  "id": "稳定事件 ID",
  "kind": "task.completed",
  "created": "事件创建时间",
  "payload": {
    "version": 1,
    "title": "任务名称",
    "executionStatus": "success",
    "assessment": { "status": "healthy", "reason": "全部正常条件满足", "findings": [] }
  }
}
```

事件类型为 `task.completed`、`task.failed`、`task.recovered`、`channel.test`。`Idempotency-Key` 为稳定投递 ID，`X-AIOps-Event-Id` 为事件 ID。配置签名密钥时，`X-AIOps-Timestamp` 是毫秒时间戳，`X-AIOps-Signature` 是 `HMAC-SHA256(secret, timestamp + "." + 原始请求正文)` 的十六进制摘要。接收方先核验签名及时间窗口，再按稳定投递键去重；重试正文和幂等键相同，时间与签名会更新。配置 Token 时同时发送 Authorization Bearer。

通用接收端用 HTTP 2xx 确认接收，业务接受失败应返回非 2xx；企业微信适配器额外核对 errcode。原 `NOTIFICATION_WEBHOOK_URL/SECRET` 仍承载已有执行异常和变更事件，保留旧正文 HMAC 协议，不与新渠道混用签名公式，也不会自动变成任务订阅。

## 已实现边界与验收

外部监控系统的通用告警接收、来源适配、分组/抑制、严重级别升级、AI 异步诊断和自动处置属于后续阶段。本期新增的是出站通知；原签名 Runbook 入口不变。

当前适配单实例 SQLite，没有独立消息中间件、跨实例租约或自动清理通知历史的留存策略。高频长期巡检应监控数据目录容量、设置合适的提醒间隔并定期备份。密钥轮换包括通知渠道密文。

自动化使用临时数据库、本地模型/MCP 协议 fixture 与 Webhook 接收端，命令为 `node --test tests/notifications.test.mjs` 和 `npm run test:notifications:browser`。2026-09-22 已在当前 Mac 通过页面配置真实企业微信机器人，确认测试消息与 DTS 单次定时巡检报告均收到企业微信成功回执；真实工具数据、状态/新鲜度判定、页面回看和单次自动停用已验证。长期周期运行、其他环境的出站代理/防火墙和群成员已读仍需另行验收，详见[验证记录](verification.md)。
