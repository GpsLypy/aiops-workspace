## 动机

当前自行维护模型/工具循环、上下文与协议适配；未来复杂排障、结构化输出、多 Agent 和长上下文会增加维护成本。AgentScope 2.0.8 提供相应基础，但无法直接替代当前权限、发布、持久审批、执行台账和巡检通知语义。

## 推荐变更

抽离 AgentRuntime，保留 LegacyRuntime，增加 Python AgentScope Worker。现有 React、Express API、SQLite、MCP 执行器、定时任务、Runbook、巡检判定与通知继续承担业务职责。用外部工具执行事件桥接现有执行器；模型首期经受限 Node 桥接，保持密钥、出口策略与统一预算。

先做 5–8 人日 PoC；通过后，达到现有能力基本等价预计总计 30–45 人日（含 PoC）。如选择完整 Python 后端重建、保留前端，预计 65–95 人日。估算假设、偏差与不含范围见报告。

## 首期范围

- AgentScope Python 固定 v2.0.8；桥接器与依赖锁固定 Python 3.12；不混用 1.x 接口。
- 单 Agent、现有文本协议、现有知识与 Skill 注入方式、受治理 MCP 工具。
- 运行时选择、模型/事件转换、持久 callId 去重、取消/故障与灰度回滚。
- 现有业务回归与两种运行时契约、性能/费用和代表性诊断质量对比。

## 非目标

不重做前端，不迁移生产数据库，不引入 Redis/向量库，不启用通用 Shell、Skill 脚本或自主多 Agent，不新增 DTS 写工具/区域，不改变写操作审批后独立执行的语义，不把聊天正常完成当作巡检正常。

## 决策门槛

PoC 证明模型两协议与外部工具执行可兼容；调用数/预算可统一控制；无越权或重复副作用；现有证据台账继续可用。若需要大规模修改框架私有实现或无法保证关键语义，则停止迁移并继续演进现有内核。

首期已通过确定性兼容与治理验证，采用公开扩展点，没有修改 AgentScope 包源码。第二期针对冷启动延迟引入预加载父进程与每轮独立子进程，补齐就绪、队列、清理、资源观测、容器与审计/评测工具。基准结果见 verification，仍需真实模型质量与灰度收益验证后决定生产切换。

第三期已通过默认 73/73、prefork/cold 各 90/90 回归与 DTS 180/180 确定性评测；浏览器刷新可回看发现失败，换钥恢复后审批/unknown/运行时切回符合治理语义。镜像移除非必需 npm/pip，扫描完整覆盖并输出 SBOM；可修复 HIGH/CRITICAL 为 0，残余 60 条未修复 HIGH/CRITICAL 不视为已接受风险。
